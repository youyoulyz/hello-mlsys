# 第 2 章 第一次真机 Profile 与性能校准

## 本章导读

> 第 1 章用硬件规格书上的峰值算力和显存带宽，为推理单步耗时划出了一条理论下界。但在真实 GPU 上，计算单元很少能持续跑满标称算力，显存控制器也难以长期维持满带宽，测量工具本身还会给计时带来额外扰动。怎样把理想下界校准成能够预测真机耗时的模型，又怎样判断校准后的模型在哪些工作区间内可靠、在哪些条件下会失效？
>
> 本章先引入双系数校准模型，用计算效率 $\eta$ 和访存效率 $\beta$ 把标称 Roofline 过渡到真机稳态近似。2.1 说明上卡测量前必须完成的环境准入、空闲基线记录与工具边界核查。2.2 在单个大矩阵乘上完成最小 Profile，拆解剖析工具的冷启动开销与逐核固定扰动，并建立同条件计时纪律。2.3 设计覆盖计算侧与访存侧的校准集，解释两个效率系数为何随算子尺寸和缓存命中状态漂移，以及如何选取代表区间加权拟合。2.4 对偏离代表区间的现象做物理归因，利用频率、功耗、温度与显存分配曲线区分功耗墙降频、温度墙降频与显存碎片。2.5 用未参与拟合的新形状做留出验证，划清模型的域内泛化能力与域外失效边界。2.6 把校准模型带入完整语言模型 Qwen3-1.7B，将实测墙钟时间拆解为校准预测、未覆盖 GPU 工作和干净发射空档三段。2.7 引入 CPU 参照线，把“更换硬件”与“更换推理引擎”拆分为两个正交的加速维度。章末实验与练习提供完整命令与离线存档。

## 教学目标

- 能在测量前完成环境准入检查，记录硬件空闲基线、性能剖析工具链支持范围和算子后端口径。
- 能在单个大算子上运行最小 Profile，区分冷启动初始化开销与逐核固定发射扰动，并遵守干净计时与同条件比较原则。
- 能写出双系数 Roofline 校准模型，说明 $\eta$ 与 $\beta$ 随算子区间变化的原因，并在代表区间上完成加权拟合。
- 能结合频率、功耗、温度与显存分配曲线，区分功耗墙降频、温度墙降频与显存碎片，并对留出集的域内与域外误差给出机制解释。
- 能将端到端单步耗时拆解为校准预测、未覆盖 GPU 工作与干净发射空档，并区分硬件换代与软件引擎优化各自带来的加速比。

## 双系数校准模型

如果只看硬件规格书，一张显卡就像一条标注着“每小时加工 200 件、传送带每小时运送 800 公斤原料”的产线。按标称参数算，一件需要 1 公斤原料、消耗 200 单位加工量的产品，在加工和运输两边花费的时间应该完全一样。可一旦真正开机运转，机床受制于指令调度、寄存器分配和流水线气泡，实际只能发挥六成左右的标称加工能力；而传送带在连续大批量搬运时，往往能跑到八九成标称速率。两条路径打折的幅度不一样，哪一端先成为瓶颈的边界就会跟着移动。

第 1 章的标称 Roofline 模型假设硬件在计算侧达到 100% 峰值算力 $P_{\mathrm{peak}}$，在访存侧达到 100% 标称带宽 $\mathrm{BW}_{\mathrm{peak}}$。要让解析模型贴近真实硬件的稳态表现，需要为计算和访存两条路径分别乘上一个无量纲效率系数——计算效率 $\eta$ 与带宽效率 $\beta$：

$$
t_{\mathrm{nom}, c} = \max\!\left(\frac{\mathrm{FLOPs}_c}{P_{\mathrm{peak}}},\; \frac{\mathrm{Bytes}_c}{\mathrm{BW}_{\mathrm{peak}}}\right),
\qquad
t_{\mathrm{cal}, c} = \max\!\left(\frac{\mathrm{FLOPs}_c}{P_{\mathrm{peak}} \cdot \eta},\; \frac{\mathrm{Bytes}_c}{\mathrm{BW}_{\mathrm{peak}} \cdot \beta}\right).
$$

其中，$\eta \in (0, 1]$ 衡量计算受限算子实际达成的算力占 $P_{\mathrm{peak}}$ 的比例，$\beta$ 衡量访存受限算子实际达成的有效带宽占 $\mathrm{BW}_{\mathrm{peak}}$ 的比例。引入这两个系数后，两条瓶颈线的交点——也就是硬件的**有效拐点**（effective ridge point）——也会随之移动。令校准后的计算耗时等于访存耗时，整理可得：

$$
\mathrm{AI}^*_{\mathrm{eff}} = \frac{P_{\mathrm{peak}} \cdot \eta}{\mathrm{BW}_{\mathrm{peak}} \cdot \beta} = \mathrm{AI}^* \cdot \frac{\eta}{\beta}.
$$

用一个手算例子可以立刻看清拐点移动的后果。假设某张 GPU 标称算力为 200 TFLOPS、标称带宽为 800 GB/s，标称拐点为 $\mathrm{AI}^* = 250\;\text{FLOP/byte}$。现在有一个算术强度为 200 FLOP/byte 的算子：在标称模型下，$200 < 250$，它被判定为访存受限，优化直觉是去压缩访存或做量化。但如果实测发现这张卡的有效计算效率只有 $\eta = 0.60$（有效算力 120 TFLOPS），而流式访存效率有 $\beta = 0.85$（有效带宽 680 GB/s），那么有效拐点就会向左移动到 $250 \times (0.60 / 0.85) \approx 176.5\;\text{FLOP/byte}$。此时 $200 > 176.5$，同一个算子在真机上其实已经跨过拐点，落入了计算受限区。

反过来，如果遇到非连续访存或跨步读取的算子，显存控制器无法把相邻请求合并成整行突发传输，有效带宽效率可能暴跌到 $\beta = 0.30$（有效带宽仅剩 240 GB/s），而计算效率仍为 $\eta = 0.60$。此时 $\eta / \beta = 2.0$，有效拐点就会向右大幅漂移到 $500\;\text{FLOP/byte}$，原本算术强度高达 350 FLOP/byte 的计算型算子也会被迫退化成访存受限。换言之，有效拐点向左还是向右移动，完全取决于计算与访存两条路径中“谁打的折更狠”。

真实 GPU 上，规整算子最常见的情况是 $\eta < \beta$：大矩阵乘受限于指令发射、共享内存银行冲突与功耗封顶，往往只能发挥 60%–70% 的标称矩阵算力；而连续大张量的流式读写能跑出 85%–90% 的标称显存带宽。因此，有效拐点通常会向左移动，算子比标称模型预期的更早变成计算受限。同时需要提前建立一个边界意识：$\eta$ 和 $\beta$ 并不是某块 GPU 出厂就写死的绝对常数，它们会随算子尺寸、片上缓存命中率和持续功耗状态而变化。只拿单个算子算一次“标称耗时除以实测耗时”只能得到事后比值，还称不上预测模型；只有选出代表区间拟合出稳定系数，并用未见过的新形状验证泛化误差，这两个系数才具备预测价值。怎样在测量前锁定环境、怎样选点拟合，以及怎样划清适用边界，正是本章接下来逐步展开的主线。

## 2.1 真机准入检查

### 环境快照与空闲硬件基线

在跑任何性能基准之前，应当先对目标机器执行一次环境准入检查，并把结果固化为快照文件（对应本章存档 `results/env_9070xt.json`）。这一步不是走过场的“确认代码能跑”，而是给后续所有实验立下可对照的标尺。如果机器上插着多张显卡却没显式隔离设备号，或者内核驱动与运行时版本在实验前后悄悄变动，后面测出的偏差就会无法定位。

硬件空闲基线尤其容易被忽略。现代 GPU 在没有计算任务时会自动切入低功耗节能档，核心频率与内存互联时钟都会大幅下探（例如本机空闲时 `fclk` 只有 219 MHz，而满载后会跃升至 1889 MHz）。显卡在刚开机、无计算任务时的温度、板载功耗和时钟读数，是判断后续高负载运行是否发生降频的起点。假如一台机器在实验开始前就已经因为机箱积热停在 65 °C，或者后台残留着其他用户占卡的进程，后面测出的延迟漂移就可能是外部干扰而非算子本身的特性。下表给出了本章实验平台 RX 9070 XT 的准入快照。

| 检查维度 | 本章实验环境快照（RX 9070 XT） |
| --- | --- |
| 目标 GPU 与架构 | AMD Radeon RX 9070 XT（`gfx1201` / RDNA4），15.9 GiB 显存；通过 `HIP_VISIBLE_DEVICES=1` 隔离同机第二张卡 |
| 软件栈版本 | Python 3.13.11 / PyTorch 2.16.0.dev+rocm10.1 / ROCm 7.16.26385 / 驱动 6.16.13 / Linux 6.14 |
| 标称参数基线 | BF16 矩阵峰值 195 TFLOPS，显存带宽 640 GB/s，标称拐点 304.7 FLOP/byte |
| 空闲硬件基线 | 温度 35 °C，板载功耗 26 W，内存互联时钟 `fclk` 219 MHz |

记录空闲数字的同时，还需要确认目标语言模型能够正常加载并完成一次预填充与单步解码，排除权重损坏、依赖缺失或显存越界等基础障碍。本章端到端剖析的目标模型是 Qwen3-1.7B（28 层，隐藏维 2048，中间层 6144，16 个查询头与 8 个键值头，单头维度 128，词表 151,936，启用输入输出权重共享）。空闲态记录下的 35 °C 与 26 W 将留作 2.4 节诊断时钟漂移的对照起点。

### 工具链支持边界与算子后端口径

锁定软硬件版本之后，还需要主动探测两项直接影响测量口径的边界条件：一是性能剖析工具对当前 GPU 架构的支持范围，二是框架实际调用的底层算子路径。如果跳过这一步，常常会在实验做到一半时才发现工具报错，或者用错了理论流量的计算公式。

在 ROCm 生态中，不同剖析工具的职责和支持的架构各有边界。`rocprofv3 --kernel-trace` 用于追踪 kernel 发射与 GPU 执行时间，在本机 `gfx1201` 上可用；`rocprof-compute` 的 `profile` 模式用于采集微架构深度硬件计数器，但当前版本仅支持 `gfx908`、`gfx90a`、`gfx94x`、`gfx950` 和 `gfx115x`，并不支持 `gfx1201`（若需硬件计数器，应改用 `rocprofv3 --pmc` 并按[附录 F](/appendix/appendix-f-troubleshooting/)锁定稳定性能档）；而 PyTorch 内置的 `torch.profiler` 通过 HIP activity 提供进程内时间线，可以跨架构作为端到端剖析的补充。提前查清这层边界，就能在进入正式测量前选对工具组合。

算子后端口径的探测同样直接关系到公式是否算对。探测 PyTorch 的缩放点积注意力（SDPA）后端发现：当查询头与键值头数量相等（如 MHA 16/16）时，框架允许走 `FLASH`、`EFFICIENT` 和 `MATH` 三种后端；但若直接传入分组查询注意力的原始头数（GQA 16q/8kv），`EFFICIENT` 后端会拒绝执行。因此 Qwen3 系列模型在进入注意力算子前，会先调用 `repeat_kv` 把 8 个键值头展开成 16 个头，再交给融合 kernel 执行。这个实现细节决定了一件很具体的事：在 2.6 节给 Qwen3-1.7B 计算注意力层的理论访存字节数时，必须按照 `repeat_kv` 展开后的 16 头口径计数，否则理论预测与实际执行路径就会错位。

## 2.2 最小 Profile 与测量扰动

### 为什么先剖析单个大算子

确认工具可用后，不要急着把包含上千个算子的完整语言模型直接扔进 profiler。剖析工具为了记录每个 kernel 的发射时刻、起止时间和调用栈，必须在 CPU 侧插入钩子函数并写入跟踪缓冲区。如果一开始就面对满屏上千条时间线，既分不清工具是否把 kernel 归属对了，也看不出工具本身把耗时拉长了多少。

更稳妥的做法是先在单个大算子上做一次**最小 Profile**。挑一个形状规整、计算量足够大的单个 BF16 矩阵乘（例如 $4096 \times 4096 \times 4096$），它每次迭代理论上只对应 1 个 GEMM kernel。在这样一个极简场景下，既能一眼核对工具报告的 kernel 数量是不是 1，也能用“开 profiler 的单轮耗时”直接除以“无 profiler 的干净单轮耗时”，量出工具自身的测量扰动。

为了保证比较公平，所有读数必须在同一会话、同一组输入张量和同一计时协议下采集。本章采用“预热 10 次、采样 50 次、重复 3 轮取中位数”的协议，在 RX 9070 XT 上测得四组对照读数（数据见 `results/minimal_profile_9070xt.json`）：

| 读数 | 测量条件 | 实测值 | 相对干净基准比值 |
| --- | --- | ---: | ---: |
| A. 干净基准 | 无 profiler，每轮 `Event` 计时并同步 | $1.054\;\text{ms}$ | $1.000\times$ |
| B. CPU 发射开销 | 连续提交 32 次不等待同步，取单次均值 | $0.0253\;\text{ms}$ | — |
| C. `rocprofv3 --kernel-trace` | 开启 kernel 追踪时的单轮 `Event` 耗时 | $1.0665\;\text{ms}$ | $1.012\times$ |
| D. `torch.profiler` | 开启进程内剖析时的单轮 `Event` 耗时 | $1.0710\;\text{ms}$ | $1.016\times$ |

核对工具明细可以确认，两款剖析工具报告的 kernel 数量完全一致（每次迭代正好 1 个 GEMM kernel），报告的 GPU 自身执行时间也几乎重合：`rocprofv3` 为 1.036 ms，`torch.profiler` 为 1.032 ms。干净基准 1.054 ms 对应的有效算力为 $2 \times 4096^3 / (1.054 \times 10^{-3}) \approx 130.4\;\text{TFLOPS}$，约占 RX 9070 XT 标称矩阵峰值 195 TFLOPS 的 67%，与第 1 章的单算子锚定结果吻合。

表中 B 项（0.0253 ms）与 A 项（1.054 ms）之间相差四十倍，顺带揭示了 GPU 计时最容易踩的异步陷阱。PyTorch 调用一次矩阵乘时，CPU 并没有原地干等 GPU 算完，而是把一条“执行 GEMM”的指令塞进命令队列就立刻返回，这叫**异步发射**。如果不调用同步接口（`Event.synchronize()` 或 `torch.cuda.synchronize()`）等待 GPU 清空队列，CPU 端秒表量到的其实只是 B 项那 25.3 微秒的“填单入队时间”，而不是 1.054 ms 的真实计算耗时。反过来，把干净基准 1.054 ms 减去 GPU 自身执行时间 1.032 ms，剩下的约 22 微秒恰好与单次 CPU 发射和同步开销吻合，整条时间线严丝合缝。

### 冷启动开销、逐核固定扰动与计时纪律

看到表中 C、D 两项只有 1.2%–1.6% 的耗时膨胀，很容易产生一个危险的错觉：“profiler 的开销不到 2%，可以放心直接拿开启 profiler 后的总时间当成真实耗时。”要识破这个错觉，需要把剖析工具的开销拆成两笔完全不同的账。

第一笔是**冷启动初始化开销**。就像工厂刚打开质检记录仪时需要校准设备，程序刚进入剖析上下文的第一轮迭代，往往会伴随约 1 ms 的一次性初始化与缓冲区分配成本。对于单次仅需 1 ms 的矩阵乘，如果不把预热迭代放进剖析窗口，只抓首轮样本，算子耗时就会显得凭空翻了一倍。只有把预热和足够多次的稳态采样一并纳入剖析区域再取中位数，才能把这笔一次性成本剔除出去。

第二笔是**逐核固定发射开销**。剖析工具是在每一次 kernel 发射时登记时间戳和元数据的，这就像高速公路收费站对每一辆车收取固定的登记时间，而不管车厢里拉的是 1 吨货还是 50 吨货。假设每发射一个 kernel，profiler 在 CPU 侧多花约 15–20 微秒做记录。当整个工作负载只有 1 个运行 1,000 微秒（1 ms）的大 GEMM kernel 时，多出的 15–20 微秒只占总时长的 1.5% 左右，几乎看不出来；可一旦负载变成 2.6 节那样、单步解码就要发射 1,591 个微小 kernel 的完整语言模型，这笔固定登记成本就会被乘上 1,591 次：

$$
1{,}591 \times 17\,\mu\text{s} \approx 27\;\text{ms}.
$$

原本 30 ms 的单步解码，挂上 profiler 后硬生生多出二十多毫秒的记录开销，端到端耗时直接膨胀到接近 1.9 倍。换言之，剖析开销是按 **kernel 发射次数**线性累加的，而不是按**计算时间**等比例缩放的。

由这两笔账直接引出贯穿全书的**计时与剖析纪律**：性能剖析工具用来观察 kernel 构成、热点排序和 GPU 自身执行时间，绝不直接用来报端到端墙钟时间。凡是要汇报“干净墙钟时间”，必须在彻底关闭 profiler 的条件下单独测量。更重要的是，当需要计算“墙钟时间与 GPU 自身执行时间之差”以评估 CPU 发射空档时，必须守住口径边界：如果拿开启 profiler 时的墙钟时间去减 GPU 自身时间，差值里混进了大量 profiler 自身制造的逐核记录膨胀；只有用无 profiler 测得的干净墙钟时间，去减 profiler 报告的 GPU 自身执行时间，才能还原出真实运行时 GPU 等待 CPU 发射的空档。2.6 节的端到端拆解会用真机数字展示违反这条纪律会带来多大的误判。

## 2.3 校准集设计与双系数拟合

### 效率系数为何随算子区间漂移

最小 Profile 确认了测量链路可靠之后，下一步就是选取一组涵盖计算侧与访存侧的基准算子作为**校准集**，在 RX 9070 XT 上按同一套协议（预热 10 次，采样 50 次，3 轮取中位数）逐一实测（数据见 `results/cal_9070xt.json`）。对每个算子，用第 1 章算出的标称下界除以实测中位数，就得到该算子的逐点效率系数：计算受限算子记为 $\eta_i = t_{\mathrm{comp}, i} / t_{\mathrm{meas}, i}$，访存受限算子记为 $\beta_i = t_{\mathrm{mem}, i} / t_{\mathrm{meas}, i}$。

| GEMM | $4096^3$ | $1365.3$ | $0.7048$（计算） | $1.0668$ | $\eta = 0.6607$ | 是 | 计算甜区代表点 |

把表里的逐点系数画在坐标轴上，立刻就能看出为什么不能把所有测点不加筛选地一股脑塞进拟合器。计算侧的 $\eta$ 沿着矩阵尺寸走出了一条“中间高、两头低”的拱形曲线：当矩阵规模只有 $2048^3$ 时，总计算量偏小，切分出来的计算块就像派给几十名工人的零碎任务，最后一轮里总有一部分计算单元提前收工干等（硬件上称为**波次量化**或尾波空转），再加上首尾流水线排空占比偏高，$\eta$ 只能跑到 $0.4848$；扩大到 $4096^3$ 与 $5120^3$ 后，每个计算单元都有足够多的计算块排队衔接，尾波空转被摊薄，矩阵管线被充分喂饱，$\eta$ 抬升到 $0.6607$ 与 $0.6072$ 的计算甜区；可继续放大到 $8192^3$ 时，单次矩阵乘执行超过 11 ms，整张卡长时间贴着功耗上限运转，动态降频又把 $\eta$ 压回了 $0.4730$。

访存侧的 $\beta$ 跨度同样剧烈。对于 $2048 \times 1024$ 的小尺寸 LayerNorm，标称读写耗时只有 13.1 微秒，还不如一次 kernel 发射与同步的固定开销长，有效带宽被发射延迟腰斩，$\beta$ 仅剩 $0.4891$。当张量扩大到 $8192 \times 4096$（单次读写合计 134 MB，远超片上缓存容量）时，发射延迟占比跌到 10% 以下，片上缓存也装不下整个工作集，LayerNorm 和 Softmax 的实测效率都平稳落在 $0.90$ 左右（$0.8996$ 与 $0.9113$），这才是真实反映片外显存流式读写的带宽平台。

### L2 缓存命中与表观带宽效率

表里最反直觉的数字出现在 Softmax $4096 \times 4096$ 这一行：标称访存下界是 0.1049 ms，真机实测居然只用了 0.0803 ms，算出来的表观效率系数 $\beta = 1.3061 > 1$。难道 GPU 跑出了超过物理显存带宽上限的速度？

当然没有。这就像清点仓库货运速度时的一个常见错觉：账面上登记今天要处理 100 箱货，你假设全部 100 箱都必须从远处的大仓库用卡车拉过来；但实际上有 35 箱昨天就已经摆在手边的货架上，卡车只跑了 65 箱的趟数就完成了任务。如果你依然拿账面上的 100 箱除以卡车跑 65 箱所用的时间，算出来的“卡车表观运力”就会超过卡车的物理极速。

回到 GPU 的访存层级，第 1 章的标称流量公式做了一个“零片上缓存复用”的简化假设：它默认算子的全部输入张量和输出张量都必须穿过片外显存控制器（HBM / GDDR）。对于 BF16 的 Softmax $4096 \times 4096$，输入和输出张量各占 $4096 \times 4096 \times 2 = 33.55\;\text{MB}$，合计约 67.1 MB。而现代 GPU 的片上 L2 缓存（以及 RDNA 架构的 Infinity Cache）容量恰好能吃下相当大一部分工作集，连续循环测试时，前一次留下的张量或中间读回数据直接命中片上缓存，根本没有穿过片外显存总线。

用一个小算式就能估算缓存吸收了多少流量。如果真实穿过片外显存的带宽效率仍按流式平台 $\beta_{\mathrm{real}} = 0.90$ 计，那么在实测 0.0803 ms 内，片外显存实际搬运的字节占比大约只有 $(0.0803 \times 0.90) / 0.1049 \approx 68.9\%$——也就是说，至少有三成以上的标称流量被片上缓存悄悄截留了。由此可以总结出一条校准选点原则：**测量显存带宽效率 $\beta$ 时，工作集必须显著大于片上末级缓存容量**，否则测到的只是“缓存命中红利”，而非真正的片外流式带宽。

### 代表区间选取与加权拟合

弄清每个异常点的物理成因后，拟合规则就非常清晰了：只选取处于稳态代表区间内的测点——计算侧选取充分饱和且尚未严重降频的 GEMM $4096^3$ 与 $5120^3$，访存侧选取工作集远超末级缓存的流式算子 LayerNorm $8192 \times 4096$ 与 Softmax $8192 \times 4096$。

为什么采用“总标称耗时除以总实测耗时”的加权公式，而不是把各点的逐点系数简单求算术平均？因为简单算术平均会把一个耗时 0.02 ms 的极小算子和一个耗时 2 ms 的大算子赋予相同权重，让小算子的微秒级测量噪声主导拟合结果；而按耗时总和加权，相当于按实际执行时间分配话语权，保证最终系数对总耗时预测的偏差最小：

$$
\eta = \frac{\sum t_{\mathrm{comp}}}{\sum t_{\mathrm{meas}}} = \frac{0.7048 + 1.3766}{1.0668 + 2.2671} = 0.6243,
\qquad
\beta = \frac{\sum t_{\mathrm{mem}}}{\sum t_{\mathrm{meas}}} = \frac{0.2097 + 0.2097}{0.2331 + 0.2301} = 0.9054.
$$

把这组代表区间系数代回双系数模型，RX 9070 XT 的有效矩阵算力为 $195 \times 0.6243 \approx 121.7\;\text{TFLOPS}$，有效显存带宽为 $640 \times 0.9054 \approx 579.5\;\text{GB/s}$，有效拐点随之从标称的 304.7 FLOP/byte 向左移动至 $304.7 \times (0.6243 / 0.9054) \approx 210.1\;\text{FLOP/byte}$。这意味着在 RX 9070 XT 上，算术强度落在 210 到 305 FLOP/byte 之间的算子，按规格书看还在访存受限区，但实际一上卡就会先撞上矩阵算力上限。

不妨顺手检验一下“把异常点混进拟合”会带来什么后果。如果把功耗墙降频的 $8192^3$（标称 5.6385 ms、实测 11.9214 ms）一起打包进加权公式，因为它的绝对耗时占了总和的大头，拟合出的计算效率会被硬生生拉低到 $(0.7048 + 1.3766 + 5.6385) / (1.0668 + 2.2671 + 11.9214) \approx 0.5061$，比真实甜区效率偏低将近两成；拿这个被污染的系数去预测 2.5 节的 $6144^3$ 留出点，预测耗时就会系统性地高估近 18%。同样，如果把命中 L2 缓存的 Softmax $4096 \times 4096$ 混进访存拟合，表观带宽效率就会虚高，导致模型低估真正吃片外显存的大张量耗时。先按物理机制剔除异质测点、再在同质代表区间内加权拟合，是保证校准模型可迁移的关键一步。

## 2.4 误差归因

把偏离代表区间的测点排除出拟合后，不能把它们当成“异常噪声”随手丢掉，而要通过受控测量查明背后的物理机制。真实 GPU 上最常见的三类系统性偏差分别来自**时钟降频**、**显存碎片**与**工具/架构口径不一致**。

### 从三条曲线区分功耗墙与温度墙

2.3 节留下了一个悬念：GEMM 放大到 $8192^3$ 后，计算效率为何从 $0.66$ 一路跌到 $0.4730$？面对持续高负载下的性能下滑，工程上最容易混淆两种截然不同的热电机制——**功耗墙降频（power-cap throttling）**与**温度墙降频（thermal throttling）**。要区分它们，不能只盯着耗时看，而要把核心时钟、板载功耗与核心温度三条曲线并排对齐观察。

先看两者的典型信号特征。如果触发的是**温度墙**，热量在散热器来不及排走时不断积聚，核心温度会一路攀升到 90–100 °C 以上的保护阈值；撞线之后，硬件被迫大幅砍掉核心频率，板载功耗也会跟着骤降，以求把温度压回安全线以下。如果触发的是**功耗墙**，核心温度往往还处在温和区间，离保护阈值很远，但芯片瞬时功耗已经顶到了板卡供电与固件设定的瓦数上限；为了不超瓦数，硬件会在功耗始终贴着上限的一条横线运转的同时，缓慢压低核心频率来为电压和电流腾出余量。

为了检验 RX 9070 XT 上的降频属于哪一种，可以对 GEMM $4096^3$ 设计一段“冷态基准—持续 60 秒满载—热态复测”的受控诊断实验，并在后台每隔 1.5 秒用 `rocm-smi` 采样核心时钟 `sclk`、互联时钟 `fclk`、板载功耗与核心温度（数据见 `results/clock_drift_9070xt.json`）。

观测结果显示出教科书般的功耗墙特征。从单步耗时看，空闲刚启动时的冷态中位数（fresh）为 1.1145 ms，持续满载 60 秒后立刻复测的热态中位数（hot）升至 1.1667 ms，增幅 **+4.68%**；持续负载期间每 200 次迭代的分块中位数从 1.1136 ms 平缓爬升至 1.1700 ms（+5.1%），全程没有出现阶跃式的断崖暴跌。把三条硬件遥测曲线对齐到同一时间轴上：负载启动约 5 秒内，核心时钟 `sclk` 短暂冲高至峰值 2496 MHz，随后在 60 秒内单调回落至 2428 MHz；与此同时，板载功耗牢牢贴在 316–333 W 的板功耗上限横线上，内存互联时钟 `fclk` 全程纹丝不动地维持在 1889 MHz，而核心温度仅从 53 °C 温和升至 67 °C，距离消费级 GPU 的温度降频红线还差得很远。

这组联动曲线直接排除了温度墙，把原因锁定在**板载功耗上限导致的动态降频**。这也反过来解释了为什么 $8192^3$ 矩阵乘的 $\eta$ 会跌至 $0.4730$：短促执行的 $4096^3$ 能在功耗墙完全生效前享受到更高的加速频率，而单次执行超过 11 ms 的 $8192^3$ 全程贴着 330 W 的功耗红线运行，核心频率被持续压低。区分这两种墙有很直接的工程意义：如果是温度墙，改善机箱风道或更换更强的散热器就能立竿见影地拉回频率；但如果是功耗墙，在板卡功耗上限不变的前提下，就算把散热器换得再好、把温度再压低 10 °C，降频现象也不会消失。

### 排除显存碎片与隔离工具链差异

持续运行几十秒后耗时变慢，除了时钟降频，另一个常见的怀疑对象是显存分配器碎片化——如果循环中不断产生临时张量而分配器又频繁触发重整或回退到低效分配路径，单步耗时也会随时间爬升。要排除这一干扰，可以在上述 60 秒持续负载的前、中、后同步采样 PyTorch 的 `memory_allocated` 与 `memory_reserved`。

实测记录表明，在整个 60 秒内，`allocated` 始终稳稳停在 0.062 GiB，`reserved` 也只在启动初期从 0.062 GiB 一次性扩张至 0.172 GiB 后就再无变化，既没有随迭代次数单调爬升，也没有反复震荡。这排除了显存碎片化对性能漂移的贡献。同时，内存互联时钟 `fclk` 全程锁定在 1889 MHz，也排除了显存总线降频的可能。

把上面几条硬件遥测曲线的判断规则收拢成一张排查清单，就能迁移到任意一张 GPU 上做性能漂移诊断：遇到持续负载变慢时，若功耗紧贴板卡上限横线、核心温度温和且时钟缓慢回落，根因是功耗墙降频；若核心温度冲到 90–100 °C 红线后频率与功耗同步骤降，根因是温度墙降频；若频率和功耗都纹丝不动，但 `reserved` 持续攀升或出现周期性卡顿，则应优先排查显存分配器碎片与临时张量泄露。至于工具链与架构口径差异（如 `rocprof-compute` 不支持 `gfx1201`、剖析工具对小 kernel 产生逐核发射膨胀，以及 SDPA 后端对 GQA 输入先做 `repeat_kv` 展开），均已在 2.1 与 2.2 节的准入和最小 Profile 阶段显式记录并隔离，不会污染硬件效率系数 $\eta$ 和 $\beta$ 的估计。

## 2.5 留出验证与模型适用域

### 冻结预测与域内泛化检验

用代表区间拟合出 $\eta = 0.6243$ 和 $\beta = 0.9054$ 之后，模型在拟合点上的贴合度只能说明“它记住了这几个点”，并不能证明它能预测没见过的新形状。在性能建模里同样存在与机器学习类似的数据泄露风险：如果先看了新形状的真机耗时，再回头微调选点规则去凑出低误差，那组测点其实已经参与了模型设计，不能再充当泛化证据。因此必须严格执行**留出验证**（holdout validation）：挑选一批未参与拟合的新配置，在执行真机实测之前，先把模型给出的预测耗时冻结并写入磁盘（在 `results/cal_9070xt.json` 中，`holdout_prediction.stored_at` 时间戳严格早于实测时间），之后再跑真机对比。

留出集刻意分成两组，承担不同的验证任务。第一组是与校准代表区间同属“饱和计算”或“大张量流式访存”的新尺寸，包括更大的矩阵乘 GEMM $6144^3$、以及单次读写规模翻倍至 268 MB 的 LayerNorm $16384 \times 4096$ 和 Softmax $16384 \times 4096$，用来检验模型的**域内泛化**能力。第二组则故意跨出校准集覆盖的算子类型，选用单请求（$b = 1$）的融合 MHA16 注意力算子（序列长度 $S = 512$ 时算术强度 $\mathrm{AI} = 256$ 落在标称访存侧，$S = 1024$ 时 $\mathrm{AI} = 512$ 落在标称计算侧），用来做**域外压力测试**。

先看域内三项的表现。无论是首次见到的 $6144^3$ 矩阵乘（相对误差 $+2.1\%$），还是张量规模翻倍的 $16384 \times 4096$ LayerNorm（$-2.2\%$）与 Softmax（$-3.4\%$），预测值与真机实测的偏差全部落在 **$\pm 3.5\%$ 以内**。反算它们的逐点效率系数，$\eta = 0.6112$ 紧贴拟合值 $0.6243$，$\beta = 0.9261 / 0.9372$ 紧贴拟合值 $0.9054$。这说明只要新算子依然停留在“饱和计算”或“流式访存”区间，仅仅靠两个标量系数，就能对不同尺寸的同类算子做出相当准确的预测。

### 域外压力测试与低并行度边界

视线移到表格下半部的域外注意力算子，误差瞬间放大到了 $+72.6\%$ 甚至 $+264.1\%$，模型出现了系统性的**偏乐观**预测。以 $S = 512$ 为例，校准模型预测只需要 0.0145 ms，真机实际却跑了 0.0527 ms，慢了三倍半以上。

这种偏差并不是公式推错了，而是双系数模型隐含的一个前提条件在这里失效了：$\eta = 0.6243$ 和 $\beta = 0.9054$ 是在“全卡计算单元被充分并行喂饱”的饱和区间上拟合出来的。而当批大小 $b = 1$、序列长度 $S = 512$ 时，单个融合 SDPA kernel 切分出的线程块数量非常有限，GPU 上大量计算单元处于闲置等待状态，再加上注意力内部还需要做在线 Softmax 归约和同步，整个算子在 $S = 512$ 时只发挥出 21% 的矩阵峰值算力（40.7 TFLOPS），拉长到 $S = 1024$ 也不过发挥出 36%（70.5 TFLOPS），远低于甜区 GEMM 的 62.4%。同时，$S = 512$ 的总执行时间只有 52.7 微秒，固定发射开销也在其中占了不小的比例。

域外偏差不仅帮我们划清了双系数模型的适用边界——它刻画的是**饱和执行区间的有效速率上界**，在低并行度、极短耗时或受同步制约的算子上会给出乐观下界——还反过来指明了后续章节系统优化的方向：要么增大批大小（batching）把计算单元填满，把算子推回饱和甜区；要么通过算子融合减少片外读写与发射次数。

## 2.6 端到端模型剖析与三段拆解

由于性能剖析工具的额外记录开销主要发生在 CPU 发射端，单个 kernel 真正跑在 GPU 硬件上的执行时长 $\sum t_{\mathrm{self}}$ 几乎不受干扰。因此，只要用关闭 profiler 测得的**干净墙钟时间** $t_{\mathrm{clean}}$，与剖析态提取出的 **GPU 自身执行时间之和** $\sum t_{\mathrm{self}}$ 以及**校准预测耗时** $\sum t_{\mathrm{cal}, c}$ 配合，就能把一次完整前向的耗时拆成互不重叠的三段：

1. **校准模型已覆盖的 GPU 工作**（$\sum t_{\mathrm{cal}, c}$）：模型按双系数公式算出的理论执行时间。
2. **模型未覆盖的 GPU 工作**（$\sum t_{\mathrm{self}} - \sum t_{\mathrm{cal}, c}$）：GPU 实际在忙、但校准模型没有算进去或低估了的时间。
3. **干净发射空档**（$t_{\mathrm{clean}} - \sum t_{\mathrm{self}}$）：GPU 已经干完上一个核、正在干等 CPU 把下一个核发下来的纯空闲时间。

### 解码与预填充的瓶颈差异

把三段拆解柱状图并排摆放，解码与预填充两个阶段截然不同的瓶颈结构一目了然。

**解码阶段（$B = 1, \mathrm{ctx} = 1024$）受“发射空档”与“未建模逐元素小核”双重主导。** 28 层 Transformer 前向一共要发射 1,591 个 kernel，平均每个 kernel 在 GPU 上只跑不到 10 微秒，CPU 逐核提交的固定间隔却把总耗时撑出了 15.17 ms 的干净发射空档（平均约 9.5 微秒/核），导致 GPU 整整一半时间处于空闲等待。再往 14.943 ms 的实际 GPU 工作内部细查 `top_kernels` 明细：矩阵乘（`Cijk` 系列）约占 6.95 ms（校准预测 5.938 ms，吻合度约 85%），融合注意力（`flyc_attn_fwd`）约占 0.88 ms（校准预测 0.811 ms，吻合度约 92%）——Roofline 建模的两大主角都预测得相当准确。真正造成 8.19 ms 未覆盖缺口的，是隐藏在主干算子缝隙里成百上千个未融合的逐元素、归约、拷贝与类型转换小核（`elementwise_kernel`、`reduce_kernel`、`CatArrayBatchedCopy` 等），而解析模型此前把它们粗略估成了 0.005 ms。

**预填充阶段（$S = 512$）已接近 GPU 饱和，缺口几乎全部留在 GPU 侧。** 虽然预填充发射的 kernel 总数（1,617 个）与解码（1,591 个）几乎完全相同，但每个 kernel 处理的是 512 个 token 而非 1 个 token，单个 kernel 的平均 GPU 执行时间从解码的不到 10 微秒拉长到了 $36.402 / 1.617 \approx 22.5\;\mu\text{s}$，其中主力矩阵乘更是长达数百微秒到数毫秒。这就像流水线上的加工工位变慢了，传菜员（CPU）提前把后面十几道菜的单子排进命令队列后，厨房（GPU）根本来不及空闲，CPU 发射开销被完全掩盖在了 GPU 的异步执行后台。因此发射空档被压缩到了微不足道的 1.93 ms，GPU 忙碌比例跃升至 95.0%。此时真正值得关注的，是高达 21.44 ms 的未覆盖 GPU 工作，它主要来自两个源头：其一，输入长度 $M = 512$ 的矩阵乘远未达到 $4096^3$ 那样的计算甜区，直接套用甜区效率 $\eta = 0.6243$ 偏乐观；其二，同样存在大量未融合的逐元素与内存拷贝小核在消耗 GPU 执行时间。

这种三段拆解把“盲目优化”变成了“按图索骥”：面对解码阶段，首要杠杆是用 CUDA/HIP Graphs 把 1,591 次零散发射打包成一次提交，并辅以算子融合与批处理，直接砍掉那 15.17 ms 的空闲等待和 7–8 ms 的碎片小核；而面对已经 95% 饱和的预填充阶段，引入 CUDA Graphs 最多只能省下 1.93 ms（约 5%），真正的优化重心必须放在算子融合和面向实际矩阵形状的核效率优化上。

## 2.7 硬件与软件的正交对照：CPU 参照线

### 控制变量：分离硬件加速与软件引擎差异

讨论大模型推理速度时，一个非常常见的表述误区是把“换用 GPU”和“换用高效推理引擎”混为一谈。好比把一辆开在平整高速路上的跑车，和一辆骑在泥泞土路上的自行车比速度，然后把几十倍的差距全部归功于发动机——这显然把“换车”和“修路”两个完全不同的因素搅在了一起。

要拆清这两个正交维度，必须严格控制变量：固定同一个模型（Qwen3-0.6B，F16 GGUF）和同一个高效推理引擎（`llama.cpp` 的 `llama-bench`，标准工作负载为 512 token 预填充 `pp512` 与 128 token 生成 `tg128`，批大小 $B = 1$，重复 5 次取中位数以消除首轮预热凹陷），仅把执行设备从 12 核 CPU（AMD Ryzen 9 3900X，`-ngl 0 -t 12`）切换到全层上卡的 RX 9070 XT（`-ngl 999`），结果记录在 `results/cpu_refline_9070xt.json`：

2. **软件引擎维度（固定 RX 9070 XT，PyTorch eager 换 `llama.cpp`，约 $4.75\times$）**。硬件一动不动，都在同一张 RX 9070 XT 上跑 Qwen3-0.6B 解码，采用高度融合 kernel 与极低发射开销路径的 `llama.cpp` 跑出了 162.28 tok/s，是逐核发射的 PyTorch eager 模式（34.13 tok/s）的 4.75 倍。

这组 4.75 倍的同卡差距，从软件实现侧直接印证了 2.6 节的三段拆解诊断：PyTorch eager 慢并不是 GPU 算力不够，而是上千次微小 kernel 的 CPU 发射空档与未融合逐元素小核拖垮了端到端表现。仅靠软件栈把这两笔开销削掉，就能在完全不换显卡的前提下收获接近五倍的提速。反过来，这也警示了评测基准里常见的一类失真宣传：如果有人把“GPU 上跑高度融合的 `llama.cpp`（162.28 tok/s）”去和“CPU 上跑未优化的 PyTorch eager”直接相除，就会把约 $9\times$ 的硬件换代收益和数倍的软件引擎收益乘在一起，夸大成“换用 GPU 带来了几十倍硬件加速”。只有把“硬件”和“引擎”拆成两个正交维度分别固定对照，才能说清每一倍加速究竟花钱买在了硬件上，还是花功夫写在了软件里。

### 无独立 GPU 时的 CPU 参照线

对于手边暂时没有独立 GPU 的读者，Roofline 模型与本章的校准方法在 CPU 上同样成立——只需要把 $P_{\mathrm{peak}}$ 换成 CPU 的向量/矩阵峰值算力，把 $\mathrm{BW}_{\mathrm{peak}}$ 换成主存通道带宽，再遵循同样的“准入 → 最小 Profile → 校准拟合 → 留出验证”流程即可。实际练习时，可以先在本机 CPU 上运行 `llama-bench -ngl 0` 测出自己的解码与预填充吞吐作为实测锚点，再结合本章代码目录下的离线存档完成全部校准、归因与三段拆解计算。

## 实验：准入、校准、留出验证与端到端拆解

## 练习

1. 某 GPU 的 BF16 标称峰值为 200 TFLOPS，标称显存带宽为 800 GB/s。经代表区间校准后测得计算效率 $\eta = 0.60$、访存效率 $\beta = 0.85$。分别求该卡的标称拐点 $\mathrm{AI}^*$ 和校准后的有效拐点 $\mathrm{AI}^*_{\mathrm{eff}}$。一个算术强度为 200 FLOP/byte 的算子，在标称模型与校准模型下分别被判定为计算受限还是访存受限？
2. 某款 GPU 在 4096³ 和 5120³ 两个计算甜区 GEMM 上的标称耗时分别为 0.70 ms 和 1.40 ms，实测中位数分别为 1.05 ms 和 2.25 ms；在 8192³ 降频点上的标称耗时为 5.60 ms，实测为 11.90 ms。按总标称耗时除以总实测耗时的口径，分别计算“仅用甜区两点”与“混入 8192³ 三点”拟合出的 $\eta$。若拿这两个 $\eta$ 去预测 6144³（标称耗时 2.38 ms，实测 3.89 ms），各自的相对误差是多少？
3. 在 2.3 节的校准表中，Softmax $4096 \times 4096$ 的标称访存下界为 0.1049 ms，实测仅需 0.0803 ms（表观 $\beta = 1.3061$）。这是否意味着该算子突破了 GPU 的物理 HBM 带宽上限？如果假设实际有效 HBM 带宽效率仍是 $\beta = 0.90$，估算至少有多大比例的标称流量被片上 L2 缓存吸收而未经过 HBM？
4. 某单算子在无 profiler 下的干净耗时为 1.00 ms，开启 profiler 后耗时变为 1.02 ms。某同学由此推断：“给一个单步包含 1,500 个小 kernel、干净耗时为 30 ms 的解码负载开启同一 profiler 后，总耗时也只会增加约 2%，即 30.6 ms。”指出这个推断错在哪里，并估算实际可能增加的耗时量级。
5. 持续运行 60 秒高负载 GEMM 时，监控日志记录到：核心温度从 50 °C 升至 65 °C，板载功耗全程维持在 320 W（接近板卡功耗上限），核心时钟从 2500 MHz 缓慢降至 2430 MHz，单步耗时上升 4.5%，显存 `allocated` 与 `reserved` 保持不变。该漂移属于功耗墙降频、温度墙降频还是显存碎片？如果更换了一套更强的散热器将温度压低到 55 °C，但功耗上限不变，这种降频会消失吗？
6. 在 2.6 节的 Qwen3-1.7B 预填充（$S = 512$）数据中，无 profiler 干净墙钟时间为 38.332 ms，开启 `torch.profiler` 后的墙钟时间为 58.563 ms，GPU 自身执行时间之和为 36.402 ms，校准模型预测的 GPU 耗时为 14.965 ms。分别计算干净发射空档、干净 GPU 忙碌比例和未覆盖的 GPU 工作时间；并说明为什么对这个预填充负载优先引入 CUDA Graphs 收益不大。
7. 在同一块 GPU 上运行同一模型解码，引擎 A 测得 35 tok/s，引擎 B 测得 160 tok/s；用引擎 B 在 12 核 CPU 上测得 18 tok/s。若有人直接拿引擎 B 的 GPU 结果（160 tok/s）除以引擎 A 在 CPU 上的结果来宣称“GPU 硬件加速了数十倍”，这个比较违背了什么原则？正确的硬件加速比与软件引擎加速比分别是多少？

::: details 参考答案

1. 标称拐点 $\mathrm{AI}^* = 200 \times 10^{12} / (800 \times 10^9) = 250\;\text{FLOP/byte}$；有效拐点 $\mathrm{AI}^*_{\mathrm{eff}} = 250 \times (0.60 / 0.85) \approx 176.5\;\text{FLOP/byte}$。对于 $\mathrm{AI} = 200$ 的算子，在标称模型下 $200 < 250$ 判为访存受限，在校准模型下 $200 > 176.5$ 转为计算受限。
2. 仅用甜区两点：$\eta_1 = (0.70 + 1.40) / (1.05 + 2.25) = 2.10 / 3.30 \approx 0.6364$，预测 6144³ 耗时 $2.38 / 0.6364 \approx 3.74\;\text{ms}$，相对误差 $(3.89 - 3.74) / 3.74 \approx +4.0\%$。混入 8192³ 后：$\eta_2 = (0.70 + 1.40 + 5.60) / (1.05 + 2.25 + 11.90) = 7.70 / 15.20 \approx 0.5066$，预测 6144³ 耗时 $2.38 / 0.5066 \approx 4.70\;\text{ms}$，相对误差 $(3.89 - 4.70) / 4.70 \approx -17.2\%$，精度显著变差。
3. 并没有突破 HBM 物理带宽上限，而是标称模型按“零片上缓存复用”高估了实际 HBM 流量。若真实 HBM 效率为 $\beta = 0.90$，则实际经过 HBM 的流量占比约为 $(0.0803 \times 0.90) / 0.1049 \approx 68.9\%$，即至少约 **31.1%** 的标称流量被 L2 缓存吸收。
4. 错在把剖析开销当成了按耗时等比例缩放的百分比（2%）。剖析开销本质上是每次 kernel 发射的固定记录成本：单核增加约 $0.02\;\text{ms} = 20\,\mu\text{s}$，若每步包含 1,500 个小 kernel，固定开销累加量级为 $1500 \times 20\,\mu\text{s} = 30\;\text{ms}$，总耗时可能膨胀至约 60 ms（接近 $2\times$），而非 30.6 ms。
5. 属于**功耗墙降频**（功耗钉死上限、温度仅 65 °C 远未触及温度墙、显存稳定排除碎片）。在板载功耗上限不变的前提下，仅降低核心温度不会消除功耗墙触发的降频（仅可能因漏电功耗略微减小而带来极小幅度缓解）。
6. 干净发射空档 $= 38.332 - 36.402 = 1.930\;\text{ms}$；干净 GPU 忙碌比例 $= 36.402 / 38.332 \approx 95.0\%$；未覆盖 GPU 工作 $= 36.402 - 14.965 = 21.437\;\text{ms}$。由于发射空档仅占整步时间的 5%，即便用 CUDA Graphs 完全消除这 1.93 ms，端到端耗时最多也只能缩短约 5%，主要优化空间在 GPU 侧算子本身。
7. 违背了控制变量（正交分解）原则，把“硬件换代”和“软件引擎差异”混在了一起。同引擎 B 下的硬件加速比为 $160 / 18 \approx 8.89\times$；同卡下的软件引擎加速比为 $160 / 35 \approx 4.57\times$。

:::
