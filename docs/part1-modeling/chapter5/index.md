# 第 5 章 通信代价模型与 Scale-in / Scale-up

## 本章导读

> 前四章围绕单张 GPU 展开：算子要做多少浮点运算、显存能装下多少权重与键值缓存、算力与显存带宽谁先触顶。一旦模型大到单卡装不下，或者单卡算得不够快，系统就必须把张量切分到多张卡上协同计算。这时，数据在不同芯片之间来回搬运的时间不再是边缘开销，而是直接决定并行策略能否成立的核心约束。
>
> 5.1 先建立硬件互联的层级直觉，区分节点内扩卡（scale-up）与节点间扩容量（scale-in）在带宽和延迟上的量级鸿沟。5.2 拆解多卡协作中最常用的集合通信原语，用极简手算推演 Ring-AllReduce 为何能在任意卡数下保持带宽最优。5.3 引入一阶 $\alpha\text{–}\beta$ 通信代价模型，找出延迟主导区与带宽主导区的分界拐点 $D^*$，并量化专用高速链路的加速区间。5.4 把通信模型放进单层 Transformer 的张量并行（TP）里，计算通信耗时占计算耗时的比例，给出“张量并行必须留在节点内”的数值依据。5.5 则从纸面公式走向真实机器，区分行为验证与性能验证，通过设备口径、引擎口径与公式口径的三方对账，展示纸面规格与实测带宽之间为何会差出数倍，以及如何在部分路径未覆盖时诚实界定证据边界。章末实验提供在线运行与离线存档核对两种路径，练习题覆盖从链路换算到三口径归因的全部计算方法。

## 教学目标

- 能区分节点内互联（PCIe、xGMI、NVLink）与节点间互联（InfiniBand、RoCEv2）的物理通路与量级差异，并把它们对应到 scale-up 与 scale-in 两条扩展轴。
- 能说清 All-Reduce、All-Gather、Reduce-Scatter 和 All-to-All 在每张卡上搬运的数据内容，并能手算推演 Ring-AllReduce 的两趟步数与单卡流量因子 $2(P-1)/P$。
- 能写出 $\alpha\text{–}\beta$ 一阶代价模型及拐点公式 $D^* = P\cdot\alpha\cdot\mathrm{BW}$，判断给定消息体量落在延迟主导区还是带宽主导区，并分析专用链路在不同体量下的加速比区间。
- 能结合计算效率模型估算张量并行（TP=2/4）单层通信占比，判断通信是否超过计算盈亏线，并解释卡数翻倍时通信占比为何呈超线性上升。
- 能区分分布式通信的行为验证（如 CPU `gloo`）与性能验证（GPU 间 NCCL/RCCL），并能对公式口径、设备口径与引擎口径的实测差异做逐级归因与边界界定。

## 5.1 硬件互联层级：节点内 Scale-up 与节点间 Scale-in

### 从单卡到多卡：数据搬运走哪些物理通路

在单张 GPU 内部，计算单元读写高带宽显存（HBM）的带宽通常达到每秒数百 GB 乃至数 TB，而且所有数据都在同一块封装或基板内流转。一旦工作拆分到两张甚至几十张 GPU 上，一张卡算出的中间结果必须跨过芯片边界送到另一张卡的显存里。此时，决定通信快慢的第一性因素并不是算法写得有多巧妙，而是两张卡之间铺着哪一条物理通路。

可以把芯片之间的数据搬运类比为城市间的交通。同在一台服务器主板内的两张 GPU，如果之间铺了专用直连总线（如 NVIDIA 的 NVLink 或 AMD 的 xGMI），就像两栋大楼之间架了专属直达廊桥，数据直接从一张卡的显存控制器发往另一张卡，不经过 CPU 和主内存。如果两张卡只插在普通主板的 PCIe 插槽上，彼此之间没有专用直连，数据往往需要先经由第一条 PCIe 链路爬到 CPU 的根复合体（Root Complex）或 PCIe 交换芯片，再沿着第二条 PCIe 链路下发到目标 GPU，这就多了一次中转。如果两张卡分属机房里的两台不同服务器，数据还必须经过网卡（NIC）、以太网或 InfiniBand 交换机以及跨机光模块，穿过网络协议栈才能抵达对端。

评估一条物理通路的能力，需要同时看清两组口径：**单向带宽与双向带宽**，以及**原始线速（raw）与有效带宽**。大多数现代高速互联都是全双工的，发送通道与接收通道各自独立，因此设备手册有时会标注双向总带宽（发送与接收相加），而算法建模通常使用单向带宽，因为环状通信中每张卡发给右邻居的流量与收自左邻居的流量各自占满一个方向。另一方面，物理层信号并不是把全部比特都用来装用户张量，它还要插入链路编码、包头、校验和流控帧。

以常见的 PCIe 4.0 $\times 16$ 为例，手算一次就能看出纸面信号速率与有效载荷之间的折损。PCIe 4.0 单通道（lane）的信号传输速率是 $16\text{ GT/s}$（每秒 160 亿次传输），16 条通道并行时的总比特率是 $16 \times 16 = 256\text{ Gbps}$。PCIe 3.0 及以上采用 $128\mathrm{b}/130\mathrm{b}$ 编码，意味着每传输 130 个物理比特，只有 128 个比特承载链路层数据。将其换算为每秒字节数（按十进制 $1\text{ GB} = 10^9\text{ B}$）：

$$
\mathrm{BW}_{\mathrm{raw}} = \frac{16 \times 16 \times 10^9\text{ bit/s}}{8\text{ bit/B}} \times \frac{128}{130} \approx 31.51\text{ GB/s}.
$$

这 $31.5\text{ GB/s}$ 只是扣除了物理层编码后的单向原始线速。在实际传输中，每个 PCIe 事务层数据包（TLP）还要附带 12–24 字节的包头和校验开销，再加上内存控制器仲裁与协议确认，工程上把 PCIe 4.0 $\times 16$ 的单向有效带宽上限通常估算在约 $25\text{ GB/s}$（约为 raw 线速的 79%）。同理，一条 $100\text{ Gbps}$ 的以太网/RoCEv2 链路，原始字节线速是 $100/8 = 12.5\text{ GB/s}$，扣除以太网帧头、IP/UDP/RDMA 协议头后，有效载荷带宽约在 $11\text{ GB/s}$ 左右（约占 raw 的 88%）。

### Scale-up 与 Scale-in 两条扩展轴

在大规模机器学习集群的设计中，把上述物理通路按作用域归类，就会自然浮现出两条扩展轴：

- **节点内扩展（Scale-up）**：在单台服务器节点内部塞入更多加速卡（常见为 4 卡或 8 卡，新一代整机柜方案进一步扩展到 72 卡域），并用极高带宽、极低延迟的本地总线把它们互联起来。通用工作站和入门级服务器走 PCIe 总线，数据中心级 GPU 节点则配备 AMD xGMI 环网或 NVIDIA NVLink / NVSwitch 专用物理层。
- **节点间扩展（Scale-in / Scale-out）**：当单个节点的物理空间、供电和散热达到上限时，需要用数据中心网络把成百上千台服务器连成一个大集群。典型技术是 InfiniBand 或基于无损以太网的 RoCEv2（RDMA over Converged Ethernet v2），通过远程直接内存访问（RDMA）绕过操作系统内核拷贝，降低跨机延迟。

为了在后文统一推导曲线、计算张量并行开销，并与真机实测做对照，本章先冻结四档具有代表性的**名义（nominal）拓扑档案**，覆盖节点内通用链路、节点内专有环网、节点内专用高速物理层以及节点间网络四个典型档位。

| 拓扑档案 | 扩展轴 | 典型物理形态 | 单向原始线速（raw） | 名义有效带宽 $\mathrm{BW}$ | 单跳启动开销 $\alpha$ |
| --- | --- | --- | --- | ---: | ---: |
| **PCIe 4.0 $\times 16$** | 节点内（scale-up） | 经 CPU 根复合体或 PCIe Switch | 31.5 GB/s（16 GT/s $\times 16$，128b/130b） | **25 GB/s** | **2 µs/跳** |
| **xGMI 环网** | 节点内（scale-up） | AMD 片间高速互联（MI300 类公开口径） | 8 链 $\times$ 64 GB/s 双向/链 | **64 GB/s** | **1 µs/跳** |
| **NVLink 300** | 节点内（scale-up） | GPU 间专用物理层（A100 单向教学口径） | 300 GB/s | **300 GB/s** | **1 µs/跳** |
| **100G RoCEv2** | 节点间（scale-in） | 跨节点 RDMA 无损以太网 | 12.5 GB/s（100 Gbps） | **11 GB/s** | **2 µs/跳** |

把这四行数字放在一起看，量级差异一目了然。在节点内这一条轴上，PCIe 4.0 $\times 16$（25 GB/s）、xGMI 环网（64 GB/s）和 NVLink 300（300 GB/s）横跨了从 25 到 300 GB/s 的区间，专用物理层相比通用 PCIe 带宽高出 $12\times$，启动延迟也压低了一半（从 2 µs 降到 1 µs）。跨出节点来到 scale-in 轴后，单口 100G RoCEv2 的有效带宽只有 11 GB/s，不仅比节点内最慢的 PCIe 还低约 $2.3\times$，与 NVLink 300 更是拉开了约 $27\times$ 的鸿沟。即便现代集群把节点间单网卡升级到 400 Gbps（有效约 44 GB/s），节点内的专用互联（如 H100/B200 世代的 NVLink4/NVLink5，单向 450–900 GB/s）也在同步翻倍，**节点内带宽比节点间高出一个数量级**的结构性落差长期存在。

::: info 本章单位换算与口径约定
后文的公式推导和脚本账本统一采用通信领域最常见的混合习惯：**消息体量**按二进制计（$1\text{ KB} = 1{,}024\text{ B}$，$1\text{ MB} = 1{,}024\text{ KB} = 2^{20}\text{ B}$，$1\text{ GB} = 1{,}024\text{ MB} = 2^{30}\text{ B}$），**链路带宽**按十进制计（$1\text{ GB/s} = 10^9\text{ B/s}$）。例如，在 $25\text{ GB/s}$ 链路上搬运 $1\text{ MB}$ 张量，纯传输时间是 $2^{20} / (25 \times 10^9) \approx 41.94\,\mu\text{s}$。

此外，上表属于**公式口径（nominal 档案）**：参数来自公开硬件规格与工程有效率估计，用于 5.3 与 5.4 的理论推演。它既不等于 5.5 中单卡主存拷贝测得的**设备口径**，也不等于双卡集合通信库拟合出的**引擎口径**。看清三者为何互不相等，正是本章最后要完成的核心对账。

### 点对点通路的瓶颈：跳数、主机中转与全双工

同样标着“PCIe 4.0 $\times 16$”，两张卡的实际通信路径却可能大相径庭。最简单的情形是单卡与主机内存之间的数据搬运（Host-to-Device，H2D；Device-to-Host，D2H），数据只走一条 PCIe 链路，称为 **1-hop**。如果是两张插在同一主板上的 GPU 互传数据，就要看硬件和驱动是否支持 PCIe 点对点直通（Peer-to-Peer，P2P）。在支持 P2P 且两卡挂在同一颗 PCIe Switch 下时，流量可以直接在交换芯片内部转发；如果两卡分别连在 CPU 的不同 PCIe 通道上，数据就必须先上行到 CPU 根复合体，再下行到另一张卡，形成 **2-hop** 路径。

当主板 BIOS 未开启大尺寸显存地址映射（Resizable BAR，简称 ReBAR），或者不同代际 GPU 之间的地址空间无法直接映射时，系统甚至无法启用硬件 P2P，只能退化为**主机内存（SHM）中转**：发送方 GPU 先把数据通过 D2H 拷贝到 CPU 共享内存，接收方 GPU 再通过 H2D 从共享内存拉取。这种中转不仅把跳数翻倍、拉高了同步延迟，还让两张卡争抢有限的 CPU 内存控制器带宽。

另一个容易被忽略的硬件属性是**全双工能力**。多卡做环状集合通信时，每张卡在同一个时间片内既要向右邻居发送一个数据块，又要从左邻居接收一个数据块。如果物理链路支持全双工且双向并发几乎不互相干扰（例如 5.5 节 V100 NVLink2 实测显示，单向 256 MB 带宽为 $144.61\text{ GB/s}$，双向并发总带宽达到 $281.53\text{ GB/s}$，每方向 $140.76\text{ GB/s}$，相对单向仅衰减 $2.7\%$），那么发送和接收就能完美重叠，算法只需按单向带宽计费；反之，若两张卡共享同一条半双工瓶颈或争抢同一个 CPU 根复合体，双向并发时的有效带宽就会进一步打折。

## 5.2 集合通信原语与 Ring 算法

### 常见集合通信原语在搬什么数据

在多卡并行训练与推理中，程序员很少手动写一堆底层的点对点 `send` 和 `recv` 来回倒腾数据，而是调用通信库（如 NVIDIA NCCL、AMD RCCL、CPU Gloo）封装好的**集合通信原语（collective communication primitives）**。它们描述的是“一组进程（通常每张 GPU 对应一个 rank）作为一个整体，数据如何从初始分布变换到目标分布”。

假设有 $P = 4$ 张卡（记作 GPU 0 到 GPU 3），每张卡上都有一块显存，用来存放长度为 4 的向量或按块切分的张量。下面用极简的符号来看看大模型系统里最常出现的几种原语到底在搬什么：

- **Broadcast（广播）**：操作前，只有 0 号卡拿着一份完整数据 $[a_0, a_1, a_2, a_3]$；操作后，4 张卡手里都有了完全相同的 $[a_0, a_1, a_2, a_3]$。常见于初始化时把 0 号卡的随机权重同步给所有卡。
- **Reduce（归约）**：操作前，每张卡各自拿着一个同形状的局部向量，比如 GPU $i$ 拿着 $v^{(i)}$；操作后，只有指定的根卡（如 0 号卡）得到了逐元素归约结果（最常见是求和 $\sum_{i=0}^{3} v^{(i)}$）。
- **All-Gather（全收集）**：操作前，每张卡只持有完整张量的四分之一分片——GPU 0 拿 $a_0$，GPU 1 拿 $a_1$，GPU 2 拿 $a_2$，GPU 3 拿 $a_3$；操作后，**每一张卡**都拼出了完整张量 $[a_0, a_1, a_2, a_3]$。在 FSDP / ZeRO-3 中，模型权重平时分散在各卡显存里，前向计算到某层之前，就通过 All-Gather 把完整权重拼出来。
- **Reduce-Scatter（归约散射）**：操作前，每张卡都持有一个长度为 4 的局部向量 $[x_0^{(i)}, x_1^{(i)}, x_2^{(i)}, x_3^{(i)}]$；操作后，每个位置上的 4 份数值分别求和，但结果并不全给同一张卡，而是分散存放——GPU 0 拿到 $\sum_i x_0^{(i)}$，GPU 1 拿到 $\sum_i x_1^{(i)}$，GPU 2 拿到 $\sum_i x_2^{(i)}$，GPU 3 拿到 $\sum_i x_3^{(i)}$。FSDP / ZeRO-2 与 ZeRO-3 在反向传播后同步并切分梯度，走的就是这一步。
- **All-Reduce（全归约）**：操作前，每张卡各自持有完整的局部向量 $x^{(i)} = [x_0^{(i)}, x_1^{(i)}, x_2^{(i)}, x_3^{(i)}]$；操作后，**每一张卡**都拿到完整的逐元素求和结果 $[\sum_i x_0^{(i)}, \sum_i x_1^{(i)}, \sum_i x_2^{(i)}, \sum_i x_3^{(i)}]$。数据并行（DDP）的梯度同步，以及张量并行（TP）每层前向/反向的局部输出合并，核心原语都是 All-Reduce。
- **All-to-All（全交换）**：操作前，每张卡手里都有 4 份要分别发给不同目标卡的数据（例如 GPU $i$ 持有 $[m_{i\to 0}, m_{i\to 1}, m_{i\to 2}, m_{i\to 3}]$）；操作后，GPU $j$ 收到所有卡发给自己的那一份 $[m_{0\to j}, m_{1\to j}, m_{2\to j}, m_{3\to j}]$，相当于把一个 $P\times P$ 的数据矩阵按卡做了一次全局转置。混合专家模型（MoE）的专家并行（Expert Parallelism）需要把不同 token 路由到对应专家所在的卡上，算完后再路由回来，依赖的正是 All-to-All。[Stanford CS336 第 7 讲](https://github.com/stanford-cs336/spring2025-lectures/blob/main/nonexecutable/2025%20Lecture%207%20-%20Parallelism%20basics.pdf) · [CMU 11-868 第 17 讲](https://llmsystem.github.io/llmsystem2026spring/assets/files/llmsys-17-MoE-3aa3125f9ccdd4bb7109ef077fbe9260.pdf)

| 集合原语 | 操作前每卡持有 | 操作后每卡持有 | 典型系统用途 |
| --- | --- | --- | --- |
| **All-Gather** | 完整张量的 $1/P$ 分片 | 拼接后的完整张量（体量 $D$） | FSDP/ZeRO 聚合分片权重、序列并行激活还原 |
| **Reduce-Scatter** | 完整局部张量（体量 $D$） | 归约后结果的 $1/P$ 分片 | FSDP/ZeRO 梯度归约并分片存储 |
| **All-Reduce** | 完整局部张量（体量 $D$） | 归约后的完整张量（体量 $D$） | DDP 梯度同步、TP 每层局部激活求和 |
| **All-to-All** | 发往各卡的 $P$ 份独立分片 | 来自各卡的 $P$ 份独立分片 | MoE 专家并行 token 路由与回传 |

仔细对照上表中的 **Reduce-Scatter** 和 **All-Gather**，会发现一个极其优雅的等价关系：如果先对每张卡的局部张量做一次 Reduce-Scatter，让每张卡各自拿到完整求和结果的 $1/P$ 分片，紧接着再做一次 All-Gather，把这 $P$ 份已经算好的分片拼回每张卡，最终每张卡拿到的恰好就是完整求和结果——也就是说，**一次 All-Reduce 在语义上完全等价于一次 Reduce-Scatter 加上一次 All-Gather**。这个拆解不仅是概念上的巧合，更是 Ring-AllReduce 算法能跑满多卡带宽的核心秘密。

### Ring-AllReduce 的两趟拆解与手算推演

先想一个最朴素的做法：假设有 $P$ 张卡要做 All-Reduce，张量总大小是 $D$ 字节。如果让其余 $P-1$ 张卡全部把大小为 $D$ 的张量发给 GPU 0，GPU 0 全部加完后再把大小为 $D$ 的结果广播回其余 $P-1$ 张卡，会发生什么？GPU 0 的接收网卡需要吃进 $(P-1)D$ 字节，发送网卡需要吐出 $(P-1)D$ 字节，总通信量随卡数 $P$ 线性膨胀。卡数从 2 扩到 64 时，GPU 0 的链路瓶颈直接恶化 63 倍，而其他 63 张卡大部分时间都在干等。

为了消除中心瓶颈，**Ring-AllReduce** 把 $P$ 张卡逻辑上连成一个单向环：GPU 0 发给 GPU 1，GPU 1 发给 GPU 2，……，GPU $P-1$ 发回 GPU 0。每张卡只和左邻居收数据、只向右邻居发数据，所有链路在同一时刻并行干活。

下面用 $P = 4$ 张卡、逻辑张量总大小 $D = 4\text{ MB}$ 的极简场景手算一遍完整流程。把每张卡上的 4 MB 张量均匀切成 4 个 1 MB 的分片，编号为块 0、块 1、块 2、块 3。记 GPU $i$ 初始持有的第 $k$ 块为 $x_k^{(i)}$。

**第一趟：Reduce-Scatter（共 $P-1 = 3$ 步）**。每一步中，所有 4 张卡同时向右邻居发送自己手里的某一个 1 MB 分片，同时从左邻居接收一个 1 MB 分片并累加到自己本地对应的分片上：

- **第 1 步**：GPU 0 把 $x_0^{(0)}$ 发给 GPU 1，GPU 1 把 $x_1^{(1)}$ 发给 GPU 2，GPU 2 把 $x_2^{(2)}$ 发给 GPU 3，GPU 3 把 $x_3^{(3)}$ 发给 GPU 0。收完累加后，GPU 1 手里的块 0 变成了两卡之和 $x_0^{(0)} + x_0^{(1)}$，GPU 2 手里的块 1 变成了两卡之和，以此类推。
- **第 2 步**：每张卡把自己刚才刚累加完的那一块继续传给右邻居。比如 GPU 1 把 $x_0^{(0)} + x_0^{(1)}$ 发给 GPU 2，GPU 2 加上自己的 $x_0^{(2)}$，得到三卡之和。
- **第 3 步**：每张卡再把刚累加完的块传给右邻居。GPU 2 把三卡之和发给 GPU 3，GPU 3 加上自己的 $x_0^{(3)}$，终于凑齐了块 0 的**四卡完整总和** $\sum_{i=0}^{3} x_0^{(i)}$。同一时刻，GPU 0 凑齐了块 1 的完整总和，GPU 1 凑齐了块 2 的完整总和，GPU 2 凑齐了块 3 的完整总和。

检查一下第一趟的账单：一共走了 $P - 1 = 3$ 步，每一步每张卡只发送了 $D/P = 1\text{ MB}$，所以第一趟每张卡累计发送了 $3 \times 1 = 3\text{ MB}$，也就是 $\frac{P-1}{P} D$。此时每张卡手里恰好各握着 1 个已经求完总和的完整块。

**第二趟：All-Gather（再走 $P-1 = 3$ 步）**。现在不需要再做加法了，只需把这 4 个完整块沿着环传一圈，让每张卡都凑齐全部 4 块：

- **第 4 步**：每张卡把自己手里那块完整的总和发给右邻居（GPU 3 发块 0 给 GPU 0，GPU 0 发块 1 给 GPU 1……），右邻居收到后直接覆盖本地对应位置。此时每张卡手里有了 2 个完整块。
- **第 5 步**：每张卡把刚收到的完整块再传给右邻居，此时每张卡手里有了 3 个完整块。
- **第 6 步**：再传最后一步，每张卡凑齐全部 4 个完整块，All-Reduce 结束。

把两趟合起来结算：一共经历了 $2(P - 1) = 6$ 个通信步，每一步每张卡发送和接收的体量都是 $D/P = 1\text{ MB}$。因此，**在整个 Ring-AllReduce 过程中，每张卡累计发出的字节数（以及累计收到的字节数）精确等于**

$$
V_{\mathrm{AR}} = 2(P - 1) \cdot \frac{D}{P} = 2\frac{P - 1}{P} D.
$$

在 $P = 4, D = 4\text{ MB}$ 的例子里，每张卡总共发出 $2 \times \frac{3}{4} \times 4 = 6\text{ MB}$。哪怕把卡数 $P$ 扩大到 64 甚至 1024，因子 $2(P-1)/P$ 也会死死锁在 $2$ 以下——无论集群有多大，每张卡只需要在发送通道上搬运不到 $2D$ 的数据，就可以完成全局求和与同步。相比朴素中心方案的 $(P-1)D$，Ring 算法在带宽维度上是理论最优的（可以证明，任何基于点对点链路的 All-Reduce 算法，每张卡在最坏情况下至少要发出 $2\frac{P-1}{P}D$ 的流量，因为每个分片至少需要经历 $P-1$ 次传递才能汇聚，再经历 $P-1$ 次传递才能分发）。[CMU 11-868 第 15 讲](https://llmsystem.github.io/llmsystem2026spring/assets/files/llmsys-15-ddp-165dbe3873fac21eb8b339e64bcfee28.pdf) · [Data Parallel Training 图解](https://siboehm.com/articles/22/data-parallel-training)

同理，如果只执行第二趟 All-Gather（或只执行第一趟 Reduce-Scatter），一共只需要 $P - 1$ 步，每张卡的发送流量减半为

$$
V_{\mathrm{AG}} = V_{\mathrm{RS}} = \frac{P - 1}{P} D.
$$

### 从逻辑流量到算法带宽与总线带宽

实际用 NCCL 或 RCCL 跑集合通信基准测试时，屏幕输出里常常并排出现两个带宽数字：**算法带宽（`algbw`）**与**总线带宽（`busbw`）**。很多初学者第一次看日志时会困惑：为什么 2 卡 All-Reduce 测出来的 `algbw` 和 `busbw` 数值一模一样，到了 8 卡时 `busbw` 却几乎是 `algbw` 的两倍？

原因就在刚刚推出来的因子 $2(P-1)/P$ 里。设参与集合通信的逻辑张量大小为 $D$，实测完成一次 All-Reduce 的耗时为 $t$。**算法带宽**是从应用视角看的“逻辑吞吐”，直接拿逻辑张量除以时间：

$$
\mathrm{algbw} = \frac{D}{t}.
$$

但刚才的手算已经表明，物理链路上每张卡实际搬运的数据量并不是 $D$，而是 $2\frac{P-1}{P} D$。为了衡量底层硬件链路的真实利用率，需要将算法带宽乘以这个修正系数，还原出硬件单向通道上实际跑过的速率，这就是**总线带宽**：

$$
\mathrm{busbw} = 2\frac{P - 1}{P} \cdot \mathrm{algbw} = \frac{2(P - 1)}{P} \cdot \frac{D}{t}.
$$

代入 $P = 2$，修正系数恰好等于 $2 \times \frac{1}{2} = 1$，所以双卡 All-Reduce 的 `algbw` 和 `busbw` 相等。代入 $P = 8$，系数变成 $2 \times \frac{7}{8} = 1.75$，此时 `busbw` 才是用来和网卡或 NVLink 标称单向带宽直接对比的指标。[NCCL Tests 性能指标说明](https://github.com/NVIDIA/nccl-tests/blob/master/doc/PERFORMANCE.md)

::: details 当卡数极大时：为什么通信库还会切换树状（Tree）算法
Ring 算法的单卡流量 $2\frac{P-1}{P} D$ 与 $P$ 几乎无关，在大消息下能把带宽吃满；但它的致命弱点藏在步数里——步数是 $2(P-1)$，随卡数 $P$ 线性增长。当 $P = 1024$ 且消息很小（比如几 KB）时，跑完 2046 跳的启动延迟会彻底淹没传输时间。

因此，NCCL 等现代通信库在遇到大卡数或小消息时，会自动切换到**双二叉树（Double Binary Tree）**等树状拓扑算法。在二叉树中，归约和广播的跳数只与树高成正比，步数从 $O(P)$ 骤降到 $O(\log_2 P)$，大幅压低了小消息的延迟地板；同时通过构造两棵互补的二叉树让叶节点和内部节点角色互换，依然能在大消息下保持接近满载的带宽利用率。[CMU 15-442 第 8 讲](https://mlsyscourse.org/slides/08-ML-parallelization-part1.pdf) 本章的一阶建模聚焦节点内中小规模（$P=2, 4$）的 Ring 模型，这是理解多卡通信代价最清晰的基准。
:::

## 5.3 $\alpha\text{–}\beta$ 通信代价模型与主导区拐点

### 一阶代价模型：启动开销 $\alpha$ 与传输斜率 $\beta$

知道了数据怎么搬、要搬多少字节之后，下一步是把“搬运耗时”写成一个可以提前预测的数学公式。如果每次换一个张量大小或换一种并行度，都要上真机预热、测 30 遍取中位数，做系统设计时就无从下手。

发一次点对点消息，和寄一次同城快递非常相似：不管包裹里装的是一张纸还是十本书，打包、填单、扫码入库都要花掉一段固定时间，这部分与包裹重量无关；装上货车之后，搬运和装卸的时间则与包裹重量成正比。在并行计算建模中，这个经典的线性抽象称为 **Hockney $\alpha\text{–}\beta$ 一阶代价模型**：

$$
T_{\mathrm{p2p}}(D) \approx \alpha + \beta \cdot D = \alpha + \frac{D}{\mathrm{BW}}.
$$

其中：
- **$\alpha$（启动开销 / 延迟项，单位常用 µs）**：发送一条消息必须付出的固定时间，包括敲响硬件门铃（doorbell）、内核启动（kernel launch）、协议栈封装、以及端到端握手同步。即使消息体量趋近于 0，时间也不会低于 $\alpha$。
- **$\beta = 1/\mathrm{BW}$（每字节传输耗时，单位常用 s/B）**：有效带宽 $\mathrm{BW}$ 的倒数。$\beta \cdot D$ 代表把 $D$ 字节数据推上物理链路所需的纯传输时间，与消息体量严格成正比。

把这个点对点模型套进 5.2 节的 Ring 推演里，每一跳都要付一次启动开销 $\alpha$，并传输 $D/P$ 字节。Ring-AllReduce 一共串联了 $2(P-1)$ 跳，Ring-AllGather（或 Ring-ReduceScatter）串联了 $P-1$ 跳，直接累加就得到本章核心的两条封闭公式：

$$
T_{\mathrm{AR}}(P, D) = 2(P - 1)\alpha + 2\frac{P - 1}{P} \cdot \frac{D}{\mathrm{BW}},
$$

$$
T_{\mathrm{AG}}(P, D) = (P - 1)\alpha + \frac{P - 1}{P} \cdot \frac{D}{\mathrm{BW}}.
$$

这个一阶模型隐含了三条简化假设：第一，全双工收发完全重叠，所以只计单向发包时间；第二，归约求和本身的算术时间（通常记作 $\gamma \cdot D$，因为 GPU 内部向量加法吞吐远高于外部互联带宽）相对传输时间可忽略不计；第三，网络内部无拥塞排队。在大多数节点内中小规模场景下，这三条假设足够贴近事实，但外推到跨机拥塞或极小消息时，就需要用 5.5 节的真机校准来检验其边界。[UIUC CS498 第 3 周讲义](https://minjiazhang.github.io/courses/sp26-resource/week3.2_training_dp_allreduce.pdf) · [MLSys·im 通信代价模型](https://mlsysbook.ai/mlsysim/api/physics.communication.html)

### 延迟主导区、带宽主导区与拐点 $D^*$

把 $T_{\mathrm{AR}}(P, D)$ 拆成前后两项观察：前项 $2(P-1)\alpha$ 是水平直线，后项 $2\frac{P-1}{P} \cdot \frac{D}{\mathrm{BW}}$ 是过原点的斜线。消息体量 $D$ 很小时，总时间几乎被前项钉死，哪怕把张量体积砍掉一半，通信时间也纹丝不动；消息体量 $D$ 很大时，前项微不足道，总时间几乎随 $D$ 成正比线性增长。

这两块区域的分界线，就是前后两项恰好相等的**拐点（crossover size）$D^*$**。令 $2(P-1)\alpha = 2\frac{P-1}{P}\cdot\frac{D^*}{\mathrm{BW}}$，两边同时消去 $2(P-1)$，立刻解出一个异常简洁的结果：

$$
D^* = P \cdot \alpha \cdot \mathrm{BW}.
$$

请注意，虽然 All-Gather 的总时间恰好是 All-Reduce 的一半，但因为启动项和带宽项同时减半，**Ring-AllGather 与 Ring-AllReduce 拥有完全相同的拐点 $D^*$**。

动手算两个具体数字，把抽象公式落到地面上。在 $P = 2$ 时：
- 对于 **PCIe 4.0 $\times 16$**（$\alpha = 2\,\mu\text{s}$，$\mathrm{BW} = 25\text{ GB/s}$）：
  $$D^*_{\mathrm{PCIe}} = 2 \times (2 \times 10^{-6}\text{ s}) \times (25 \times 10^9\text{ B/s}) = 100{,}000\text{ B} = \frac{100{,}000}{1{,}024}\text{ KB} \approx 97.66\text{ KB}.$$
  此时启动项为 $2(2-1)\times 2 = 4\,\mu\text{s}$，带宽项也是 $4\,\mu\text{s}$，总耗时 $8\,\mu\text{s}$。
- 对于 **NVLink 300**（$\alpha = 1\,\mu\text{s}$，$\mathrm{BW} = 300\text{ GB/s}$）：
  $$D^*_{\mathrm{NVLink}} = 2 \times (1 \times 10^{-6}\text{ s}) \times (300 \times 10^9\text{ B/s}) = 600{,}000\text{ B} = \frac{600{,}000}{1{,}024}\text{ KB} \approx 585.94\text{ KB}.$$
  此时启动项为 $2\,\mu\text{s}$，带宽项也是 $2\,\mu\text{s}$，总耗时仅 $4\,\mu\text{s}$。

这里藏着一个极易让人直觉打架的现象：**为什么更快的 NVLink，拐点 $D^*$ 反而比 PCIe 靠右了 6 倍（585.94 KB vs 97.66 KB）？** 拐点靠右并不是链路变慢了，恰恰是因为带宽太高了——NVLink 把每字节的传输斜率压低了 12 倍，而启动开销只降了一半，导致消息体量必须攒到 586 KB 这么大，传输时间才能勉强追上那区区 $2\,\mu\text{s}$ 的启动地板。拐点处的总时间公式是 $T_{\mathrm{AR}}(P, D^*) = 4(P-1)\alpha$，只和 $\alpha$ 有关。所以高速专用链路同时做到了两件事：**把延迟地板压得更低，同时把延迟主导区向右推得更宽**。

在工程优化中，$D^*$ 是一条极有价值的分水岭：
- 当业务通信落在 **$D < D^*$（延迟主导区）** 时，启动项占总耗时 50% 以上。此时花大力气换更高带宽的网卡或压缩张量精度收效甚微，真正有效的是**减少通信次数与启动开销**——例如把多次小梯度合并打包（gradient bucketing）、用算子融合减少同步点，或者用 CUDA Graphs 降低主机侧 kernel launch 延迟。
- 当业务通信落在 **$D > D^*$（带宽主导区）** 时，带宽项占主导。此时需要盯着有效带宽本身——使用更高速的物理互联、采用低精度通信（如 FP8/BF16）、或者通过异步流让通信与下一层计算重叠（compute-communication overlap）。

这张图给出了一个非常务实的选型判据：如果工作负载以几 KB 的极小消息为主（例如小批量解码阶段的轻量同步），花高价上专用高速链路，实际拿到的加速比往往只有 $1\text{–}2\times$，远不如优化启动延迟划算；只有当单次通信体量达到数百 KB 乃至数十 MB 以上（如中大批量张量并行、FSDP 权重与梯度聚合），专用物理层十倍以上的带宽红利才会真正兑现。

::: details 加速比两端的数学极限
设参考链路参数为 $(\alpha_{\mathrm{ref}}, \mathrm{BW}_{\mathrm{ref}})$，对照链路为 $(\alpha_x, \mathrm{BW}_x)$。在相同卡数 $P$ 下，Ring-AllReduce 的加速比为

$$
S(D) = \frac{2(P-1)\alpha_x + 2\frac{P-1}{P}\frac{D}{\mathrm{BW}_x}}{2(P-1)\alpha_{\mathrm{ref}} + 2\frac{P-1}{P}\frac{D}{\mathrm{BW}_{\mathrm{ref}}}}
= \frac{\alpha_x + \frac{D}{P\cdot\mathrm{BW}_x}}{\alpha_{\mathrm{ref}} + \frac{D}{P\cdot\mathrm{BW}_{\mathrm{ref}}}}.
$$

当 $D \to 0$ 时，分子分母的带宽项消失，$S(D) \to \alpha_x / \alpha_{\mathrm{ref}}$（例如 PCIe 对 NVLink 为 $2/1 = 2$，xGMI 对 NVLink 为 $1/1 = 1$）。当 $D \to \infty$ 时，启动项可忽略，$S(D) \to \mathrm{BW}_{\mathrm{ref}} / \mathrm{BW}_x$（对 PCIe 为 $300/25 = 12$，对 xGMI 为 $300/64 = 4.6875$，对 RoCE 为 $300/11 \approx 27.27$）。因为分子分母均为 $D$ 的一次函数，加速比在两端极限之间严格单调过渡。
:::

## 5.4 张量并行的通信占比与互联约束

### 单层 Transformer 的张量并行通信量

孤立地看一次通信耗时是 $0.05\text{ ms}$ 还是 $0.5\text{ ms}$ 并没有绝对意义——通信快不快，必须拿来和**同期做的计算时间**比。如果单层计算要花 $10\text{ ms}$，那么 $0.5\text{ ms}$ 的通信只占 $5\%$，完全可以接受；如果单层计算只要 $0.2\text{ ms}$，同样的 $0.5\text{ ms}$ 通信就会让多卡加速变成负收益。

以大模型训练与推理中最依赖低延迟互联的**张量并行（Tensor Parallelism，TP）**为例。在 Megatron 风格的列切分加行切分方案中，一个标准 Transformer 层包含多头自注意力（Attention）和前馈网络（MLP）两个子块。每个子块的第一层线性投影按输出维度（列）切分到 $P$ 张卡上，各自独立完成激活函数或注意力计算；第二层线性投影按输入维度（行）切分，每张卡只算出完整输出矩阵的一个局部和。为了把完整结果交给下一层的归一化（LayerNorm / RMSNorm），必须在 Attention 输出后和 MLP 输出后**各做一次 All-Reduce**——也就是**每层前向传播触发 2 次 All-Reduce**。[CMU 11-868 第 16 讲](https://llmsystem.github.io/llmsystem2026spring/assets/files/llmsys-16-model-parallel-83b41612547620ee0e172caa1ee448ed.pdf)

每次 All-Reduce 同步的逻辑张量，正是当前批次在这一层的隐藏状态激活。设批内总 token 数为 $N = B \cdot S$（批大小乘以序列长度），模型隐藏维度为 $d_{\mathrm{model}}$，每个元素占 $b_{\mathrm{elem}}$ 字节（BF16 下为 2 字节），则单次 All-Reduce 的消息体量为

$$
D_{\mathrm{payload}} = N \cdot d_{\mathrm{model}} \cdot b_{\mathrm{elem}}.
$$

以 **Qwen3-1.7B**（$d_{\mathrm{model}} = 2048$，28 层，BF16 精度）为例手算一次：当批内共有 $N = 256$ 个 token 时，每次 All-Reduce 需要同步的张量大小是

$$
D_{\mathrm{payload}} = 256 \times 2048 \times 2\text{ B} = 1{,}048{,}576\text{ B} = 1.0\text{ MB}.
$$

同一层中，每张卡分摊到的计算时间怎么估算？沿用第 2 章校准好的单卡计算模型：单层 Transformer 矩阵乘法的总浮点运算量按稠密层近似口径取 $32 \cdot N \cdot d_{\mathrm{model}}^2$（包含注意力投影与 MLP 投影的主体计算），切分到 $P$ 张卡后每卡承担 $1/P$。代入第 2 章测得的 RX 9070 XT BF16 名义峰值 $F_{\mathrm{peak}} = 195\text{ TFLOPS}$ 与计算效率系数 $\eta = 0.6243$，单卡单层计算时间为

$$
T_{\mathrm{comp}}(N, P) = \frac{32 \cdot N \cdot d_{\mathrm{model}}^2}{P \cdot F_{\mathrm{peak}} \cdot \eta}.
$$

代入 $N = 256, d_{\mathrm{model}} = 2048, P = 2$：分子总运算量约 $3.436 \times 10^{10}\text{ FLOPs}$，分母为 $2 \times 195 \times 10^{12} \times 0.6243 \approx 2.435 \times 10^{14}\text{ FLOP/s}$，相除得到单卡单层计算时间约为 **$0.1411\text{ ms}$**。

### 通信占比的计算与盈亏分界

把单层两次 All-Reduce 的总时间除以单卡单层计算时间，定义**单层通信占比**：

$$
r_{\mathrm{comm}} = \frac{2 \cdot T_{\mathrm{AR}}(P, D_{\mathrm{payload}})}{T_{\mathrm{comp}}(N, P)} \times 100\%.
$$

这个比值有一条非常直观的**100% 盈亏线**：当 $r_{\mathrm{comm}} = 100\%$ 时，通信耗时已经和计算耗时平起平坐；一旦 $r_{\mathrm{comm}} > 100\%$，说明 GPU 在每层里等数据的时间比真正算矩阵的时间还要长——哪怕不计其他开销，花两倍硬件成本做张量并行，切分算力省下来的时间也全被通信吃掉了。

### 为什么张量并行必须限制在节点内高速链路

对着上面这张表和柱状图，可以把分布式训练里一条反复被引用的经验铁律——**“张量并行组必须限制在单节点高速互联内，绝不轻易跨节点”**——拆解出三层严密的数值因果。

第一层是**节点间互联的全面失守**。在 100G RoCEv2 上，无论 $\mathrm{TP} = 2$ 还是 $\mathrm{TP} = 4$，无论批内 token 数是 64 还是 4,096，通信占比全部高于 100%（从 135.45% 到 541.34%）。原因在于大批量时，计算量与通信量都随 token 数 $N$ 线性增长（$T_{\mathrm{comp}} \propto N$，带宽主导区 $T_{\mathrm{AR}} \propto N$），$N$ 在分子分母中相互抵消。这意味着**单纯加大批量无法救活低带宽链路上的张量并行**——在 100G RoCEv2 上把 $N$ 从 256 放大 16 倍到 4,096，TP=2 的通信占比也只是从 140.77% 微降到 135.45%，永远跨不过盈亏线。

第二层是**提高 TP 并行度时的双向挤压效应**。对比表格里同一批量下 TP=2 到 TP=4 的变化，会发现通信占比并不是温和地涨 1.5 倍，而是直接跳涨了 **3 倍到近 4 倍**。以 PCIe 4.0 $\times 16$ 为例：
- 在大批量 $N = 4096$（带宽主导区）下，通信占比从 $59.80\%$ 飙升至 $180.45\%$（扩大了 $3.02\times$）。这是因为分子中的带宽流量系数 $2(P-1)/P$ 从 $1$ 涨到了 $1.5$（放大 $1.5\times$），而分母中的单卡计算时间 $T_{\mathrm{comp}} \propto 1/P$ 恰好减半（缩小 $2\times$），一升一降相乘就是 $1.5 \times 2 = 3\times$。
- 在小批量 $N = 64$（混合区，payload 仅 0.25 MB）下，情况更严峻：占比从 $82.12\%$ 暴涨至 $314.38\%$（扩大了 $3.83\times$）。这是因为分子中的启动项 $2(P-1)\alpha$ 从 $2\alpha$ 涨到了 $6\alpha$（整整 $3\times$），叠加分母减半，在极小批量纯延迟区甚至会逼近 $3 \times 2 = 6\times$ 的恶化幅度。

第三层是**专用物理层对小批量 TP 的兜底作用**。PCIe 4.0 $\times 16$ 在 TP=2 下勉强把通信占比压在 60%–82%，一到 TP=4 便全线崩溃（180%–314%）。xGMI 环网在 TP=2 下表现稳健（23%–35%），但在 TP=4 的 64 token 小批下依然冲破了红线（137.69%）。四档拓扑里，**只有 NVLink 300 在 TP=4、64 token 这种最苛刻的小批切分下依然把通信占比锁在 100% 以下（82.89%），大批量下更是低至 5.13%（TP=2）和 15.92%（TP=4）**。

此外，上述推导还有一个隐含的变量值得留意：单层计算量与 $d_{\mathrm{model}}^2$ 成正比，而单层通信量只与 $d_{\mathrm{model}}$ 成一次正比，因此**模型隐藏维度 $d_{\mathrm{model}}$ 越大，计算与通信的比值越高，越容易摊薄 TP 的通信代价**。Qwen3-1.7B 的 $d_{\mathrm{model}} = 2048$ 属于较小规模，所以 TP=4 对链路极为挑剔；当模型扩大到 70B 级别（$d_{\mathrm{model}} = 8192$）时，单层计算量暴涨 16 倍而通信量只涨 4 倍，通信占比会整体下降约 4 倍，这正是超大模型通常在单机 8 卡 NVLink 域内开到 TP=8、而跨节点则改用流水线并行（PP）或数据并行（DP）的根本原因——这一点将在第 6 章的 3D 并行组合中继续展开。

## 5.5 从纸面模型到真机实测：三口径对账与边界

纸面上的名义档案和 $\alpha\text{–}\beta$ 公式虽然整洁，但真实机器的通信行为往往比公式复杂得多。要把理论模型变成可靠的系统决策工具，必须把**公式口径（名义档案）**、**设备口径（单卡主机↔显存实测）**和**引擎口径（多卡集合通信库实测拟合）**摆到同一张台面上核对。在此之前，先要划清一条极易踩坑的边界。

### 区分行为验证与性能验证

在写分布式训练代码时，手边未必随时有昂贵的多卡 NVLink 服务器。PyTorch 的 `torch.distributed` 提供了基于 CPU 的 `gloo` 后端，可以在普通电脑甚至单卡机器上启动多个进程，跑通完整的 `all_reduce`、`all_gather` 逻辑。这种测试极具价值，但必须明确它的定位：**它是行为验证，不是性能验证**。

本章使用 `gloo_semantics.py` 在 2 个进程（2 rank）和 4 个进程（4 rank）下分别对 `dist.all_reduce` 做了五项语义核验（结果存档于 `results/gloo_semantics.json`）：

| 验证项 | 2 rank | 4 rank | 检验的通信语义 |
| --- | --- | --- | --- |
| `sum_correct` | 通过 | 通过 | rank $i$ 贡献 $(i+1)\cdot\mathrm{arange}(2048)$（FP64），归约后精确等于 $\frac{P(P+1)}{2}\cdot\mathrm{arange}(2048)$ |
| `consistent_across_ranks` | 通过 | 通过 | 通过 `all_gather_object` 核对所有进程得到的张量逐元素完全一致 |
| `in_place` | 通过 | 通过 | 原地规约后张量内存地址 `data_ptr` 不变，元素值全部更新为 $P$ |
| `dtype_bf16` | 支持 | 支持 | 记录当前 PyTorch 版本下 `gloo` 对 BF16 归约的支持边界 |
| `blocking` | 通过 | 通过 | 同步点语义：任意进程的退出时间戳均不早于最晚进程的进入时间戳 |

最后一项阻塞语义的时间戳证据尤为直观：在 2 rank 和 4 rank 测试中，各进程进入 `all_reduce` 的时刻极差（`enter_spread_s`）分别为 $2.8 \times 10^{-5}\text{ s}$ 和 $2.5 \times 10^{-5}\text{ s}$，且 `all_exit_ge_latest_enter` 均为真——没有任何一个进程在同伴尚未进入集合操作前就提前返回，这从行为上坐实了集合通信作为全局同步屏障的语义。

然而，`gloo` 在单节点多进程下走的是 CPU 内存与本地回环/共享内存路径，完全不经过 GPU 显存控制器、PCIe 或 NVLink 物理层。把 `gloo` 跑出来的毫秒数拿去和 5.3 节的 GPU 互联曲线对比，或者拿它估算集群吞吐，属于典型的口径错位。真正衡量硬件通路能力，必须进入 GPU 设备层与通信引擎层的实测。

### 设备口径：PCIe 1-hop 主机与显存传输实测

先看最基础的设备口径：单张 GPU 与主机内存之间的 1-hop PCIe 拷贝。在配备 AMD Ryzen 9 3900X（单 NUMA 节点、12 核 24 线程）与 RX 7900 XTX（PCIe 4.0 $\times 16$）的宿主上，使用锁页内存（pinned memory）运行 `pcie_probe.py`，覆盖 64 KB 延迟端以及 1 MB 到 1 GB 的 6 个倍增档位，每点做 5 次预热加 30 次 CUDA/HIP Event 计时取中位数，同时记录 64 MB 非锁页（pageable）内存作为对照（数据见 `results/pcie_probe_7900xtx.json`）。

| 传输体量 | H2D 带宽（GB/s） | D2H 带宽（GB/s） | 64 KB 单次中位耗时 |
| ---: | ---: | ---: | --- |
| **64 KB** | 2.61 | 1.38 | H2D 0.049 ms / D2H 0.047 ms |
| **1 MB** | 11.49 | 9.93 | — |
| **4 MB** | 13.67 | 12.79 | — |
| **16 MB** | 14.15 | 13.78 | — |
| **64 MB** | 14.27 | 14.06 | — |
| **256 MB** | 14.30 | 14.15 | — |
| **1 GB** | **14.31** | **14.15** | — |
| pageable 64 MB（对照） | 14.12 | 14.19 | — |

实测数据立刻抛出了一个尖锐的反差。按照 5.1 节的公式口径，PCIe 4.0 $\times 16$ 单向原始线速 $31.5\text{ GB/s}$，名义有效带宽 $25\text{ GB/s}$，测前预期稳态带宽落在 20–25 GB/s 的工程带内；但真机跑到 1 GB 彻底饱和后，稳态带宽却卡死在 **H2D $14.31\text{ GB/s}$、D2H $14.15\text{ GB/s}$**——只有名义上限 $25\text{ GB/s}$ 的约 $57\%$、理论 raw 的约 $45\%$。同时，64 KB 小消息单次同步传输耗时达到 $47\text{–}49\,\mu\text{s}$，比协议层 $\alpha = 2\,\mu\text{s}$ 高出一个量级以上。

遇到实测远低于规格书的现象，切忌直接下结论“硬件坏了”或者含糊地“乘一个经验系数了事”，正确的做法是沿着硬件栈**逐项排查并排除已知诱因**：

1. **排查链路降速**：读取 Linux `sysfs` 下的 `current_link_speed` 与 `current_link_width`，确认 RX 7900 XTX 实际协商在 `16 GT/s`（Gen4）和 `16` 通道，且当前值等于最大值，排除了主板插槽降速到 Gen3 或 $\times 8$ 的可能。
2. **排查跨 NUMA 转发**：宿主机 Ryzen 9 3900X 为单 NUMA 节点，GPU 的 `local_cpulist` 覆盖全部 24 个逻辑线程，不存在跨 CPU Socket 走片间总线绕路的问题。
3. **排查单发流水线未喂饱**：改用 8 块在途双缓冲持续拷贝测试，持续吞吐依然停在 $14.3\text{ GB/s}$，说明这不是单次提交间隙造成的空泡，而是实打实的持续带宽天花板。
4. **排查 IOMMU 页表翻译开销**：宿主在启用内核参数 `iommu=pt`（直通模式）重启前后，用完全相同的脚本复测了一遍。重启前（存档于 `results/pcie_probe_7900xtx_nopt.json`）1 GB 稳态带宽为 H2D $14.30\text{ GB/s}$、D2H $14.16\text{ GB/s}$，64 KB 耗时为 $51/49\,\mu\text{s}$，与重启后在噪声范围内完全一致，排除了 IOMMU 翻译模式的影响。

经过这四轮排除，问题被收窄到一个清晰的边界：在物理链路确已协商为 Gen4 $\times 16$、且单 NUMA 直连的前提下，实测 $14.3\text{ GB/s}$ 恰好落在 PCIe Gen3 $\times 16$ 原始线速（$15.6\text{ GB/s}$）的约 $92\%$，指向该主板芯片组/CPU DMA 引擎与当前 ROCm 驱动拷贝路径的综合效率上限。在缺乏硬件总线分析仪进一步拆解微架构事务前，这一残差应当诚实地标记为**待解残差（unresolved）**，而它给出的系统教训无比清晰：**物理链路规格只是上界，绝不能直接拿来当真机有效带宽用**。

### 引擎口径：NVLink 双卡 NCCL 标定与间隙分解

单卡 H2D/D2H 只能量出主机与显存之间的通道上限；真正的多卡并行跑的是通信库（NCCL/RCCL）的集合原语，它会把物理链路带宽、多通道切分调度、同步握手和归约计算全部揉在一起，这才是**引擎口径**。

在双卡 NVIDIA Tesla V100-SXM2-16GB（物理 GPU 4 与 GPU 5，通过 6 条 NVLink2 互联，拓扑显示为 **NV6 bond**，单 NUMA）上，运行与本章统一协议对齐的 `nccl_probe_v100nv6.py`（结果见 `results/nccl_probe_v100nv6.json`）。协议事先冻结了 12 个**校准点**（64 KB 到 128 MB，逐档翻倍）和 2 个**留出验证点**（16 KB 检验小消息外推，256 MB 检验大消息外推），使用 BF16 张量，每点 5 次预热加 30 次 CUDA Event 计时取中位数。NCCL 日志确认 12 个通信通道全部走 `P2P/CUMEM` NVLink 直连，且 `can_device_access_peer` 与数值求和校验全部通过。

在 12 个校准点上，对 $P = 2$ 的 Ring-AllReduce 线性模型 $T = a + b \cdot D$（其中 $a = 2\alpha_{\mathrm{eff}}$，$b = 1/\mathrm{BW}_{\mathrm{eff}}$）做最小二乘拟合，得到：

$$
\alpha_{\mathrm{eff}} = 24.45\,\mu\text{s/跳} \quad (2\alpha_{\mathrm{eff}} = 48.90\,\mu\text{s}), \qquad
\mathrm{BW}_{\mathrm{eff}} = 102.24\text{ GB/s}, \qquad
R^2 = 0.99965.
$$

接着用这组拟合参数去盲测两个从未参与拟合的留出点，检验一阶模型的外推能力：

| 留出测试点 | 拟合模型预测耗时 | 真机实测中位耗时 | 相对误差 | 误差归因 |
| ---: | ---: | ---: | ---: | --- |
| **16 KB**（延迟端外推） | 0.0491 ms（49.1 µs） | 0.0410 ms（41.0 µs） | **+19.77%** | 小消息区存在约 41 µs 平台地板（16/64/128 KB 均为 41.0 µs），线性截距在拐点下方轻微高估 |
| **256 MB**（带宽端外推） | 2.6746 ms | 2.6388 ms | **+1.35%** | 进入带宽主导区后线性度极高，外推误差在 1.5% 以内 |

这组留出结果精准刻画了 $\alpha\text{–}\beta$ 一阶模型的适用边界：在带宽主导区，用 128 MB 以内的数据外推到 256 MB，精度可以控制在 $1.35\%$；但在极小消息区，实测耗时在 16 KB、64 KB、128 KB 三个点上死死贴在 $40.96\,\mu\text{s}$ 的启动地板上，而全局最小二乘为了兼顾中大消息的斜率，把线性截距拉高到了 $48.90\,\mu\text{s}$，从而在拐点下方产生了接近 $20\%$ 的过估计。

更有意思的问题紧随其后：**同样叫 NVLink，为什么 5.1 节的名义档案给的是 $300\text{ GB/s}$、$\alpha = 1\,\mu\text{s}$，而 V100 双卡实测出来的引擎口径只有 $102.24\text{ GB/s}$、$\alpha_{\mathrm{eff}} = 24.45\,\mu\text{s}$，大消息耗时差了接近 3 倍（256 MB 处实测 $2.639\text{ ms}$ vs 名义 $0.897\text{ ms}$）？**

为了不靠猜、把这近 3 倍的差距一刀一刀拆开，在同一对 V100 卡上补充测量了绕过 NCCL 的**裸 P2P 显存拷贝**（`p2p_raw_probe_v100nv6.py`，结果见 `results/p2p_raw_v100nv6.json`），同时检查 `nvidia-smi nvlink -s` 确认两卡间全部 6 条 NVLink2 链路激活，单链速率 $25.781\text{ GB/s}$（标称单向 raw 合计 $6 \times 25.781 = 154.69\text{ GB/s}$，规格书常用口径为单向 $150\text{ GB/s}$）：

| 裸 P2P 测量方式 | 1 MB | 4 MB | 16 MB | 64 MB | 256 MB |
| --- | ---: | ---: | ---: | ---: | ---: |
| 单向单流（GB/s） | 47.84 | 108.68 | 133.95 | 142.24 | **144.61** |
| 单向 8 流分块并行（GB/s） | 4.18 | 18.31 | 69.77 | 110.68 | 136.04 |

同时，256 MB 双向并发总带宽达到 **$281.53\text{ GB/s}$**（每方向 $140.76\text{ GB/s}$，达标称双向总线的 $91.0\%$，全双工几乎无劣化），而 64 KB 单次裸拷贝延迟为 **$21.74\,\mu\text{s}$**。此外，单向实测 $144.61\text{ GB/s}$ 远超 V100 SXM2 主机 PCIe Gen3 $\times 16$ 的有效上限（约 12–13 GB/s），从带宽量级上也独立证实了流量确实直走 NVLink 物理层而非主机中转。

有了这组裸互联实测值作为中间锚点，名义 NVLink 300 与 V100 引擎实测之间近 $2.94\times$ 的带宽差距就被严丝合缝地分解成了两级可核对的因子：

1. **代际差异因子**：名义档案 `nvlink300` 对应的是 A100 世代的 NVLink3（单向 $300\text{ GB/s}$），而实测机器是 V100 世代的 NVLink2（单向单流裸实测 $144.61\text{ GB/s}$，为规格单向 $150\text{ GB/s}$ 的 $96.4\%$）。这一代际差贡献了 $300 / 144.61 = 2.074\times$。
2. **通信库引擎效率因子**：在 $144.61\text{ GB/s}$ 的裸链路之上，NCCL 执行 All-Reduce 需要分片流水线、通道同步和 BF16 归约，实际交付的有效带宽为 $102.24\text{ GB/s}$，引擎效率为 $102.24 / 144.61 \approx 70.7\%$，对应耗时放大系数 $144.61 / 102.24 = 1.415\times$。

两级因子相乘：$2.074 \times 1.415 = 2.935\times$，与 256 MB 留出点上实测相对名义的耗时比（$2.6388 / 0.8968 \approx 2.94\times$）完全闭合（顺带说明：存档脚本 `nccl_probe_v100nv6.py` 在生成 `nominal_comparison` 表时误将单跳 $\alpha$ 提前乘了 2，使表中名义截距为 $4\,\mu\text{s}$ 而非账本的 $2\,\mu\text{s}$；在 256 MB 大消息处这两微秒几乎不影响比值，为 $2.936\times$，但在 64 KB 小消息处按账本单跳 $\alpha=1\,\mu\text{s}$ 计，名义值应为 $2.22\,\mu\text{s}$ 而非表中的 $4.22\,\mu\text{s}$）。至于延迟项 $\alpha$ 的差距，裸单发 64 KB 拷贝已需 $21.74\,\mu\text{s}$，NCCL All-Reduce 的小消息地板 $40.96\,\mu\text{s}$ 再多出约 $19\,\mu\text{s}$，正好归因于通信库的 kernel launch 与跨卡同步开销。

### 三口径对账与未覆盖场景的证据边界

把前文的所有线索收拢到一起，就能看清多卡通信建模中最核心的方法论——**三口径对账**。以本地双卡 PCIe 2-hop 宿主（RX 7900 XTX + RX 9070 XT，经单 NUMA CPU 根复合体互联）为例，把公式口径、设备口径与引擎口径并排摆在同一张表上：

| 参数（$P=2$，PCIe 2-hop） | 公式口径（名义档案） | 设备口径（单卡 pinned 实测） | 引擎口径（双卡 RCCL 实测） | 差异归因与证据边界 |
| --- | --- | --- | --- | --- |
| **启动项 $\alpha$（µs）** | $4\,\mu\text{s}$（2 跳协议估算） | 64 KB H2D 约 $49\,\mu\text{s}$（完整启动+传输） | **未覆盖（not\_covered）** | 公式与设备差约 $12\times$ 属于**测量口径差**（协议门铃 vs 真实小传输完整闭环）；引擎层叠加 RCCL 启动与同步的增量本机未测得 |
| **有效带宽 $\mathrm{BW}$（GB/s）** | $25\text{ GB/s}$（链路名义上限） | H2D $14.31$ / D2H $14.15\text{ GB/s}$（1-hop 稳态） | **未覆盖（not\_covered）** | 设备仅达名义的 $57\%$，排查链路协商、NUMA 与 IOMMU 后指向宿主 DMA/驱动拷贝效率（残差标 unresolved）；2-hop 中转的二级折损未测得 |

![三口径对账总览图。子图 A 展示 7900 XTX 在 1 MB 至 1 GB 下的 H2D/D2H pinned 实测带宽稳定在 14.2–14.3 GB/s，明显低于灰色 20–25 GB/s 工程预测带；子图 B 示意本地双卡经 CPU 根复合体的 2-hop PCIe 拓扑及 RCCL 双进程无法完成首个 All-Reduce 的诊断签名；子图 C 对比 PCIe 2-hop 公式口径与设备口径的有效带宽及对数坐标下的启动项，并标注引擎口径未覆盖。](./images/fig4-reconciliation.png)

为什么这张表里本地 PCIe 2-hop 的引擎口径诚实地写着 **未覆盖（`not_covered`）**，而不是找个近似数字填进去？这是系统性能工程中极重要的一条纪律：**测不出来或环境卡死时，保留诊断证据比硬凑拟合更有价值**。

在这台跨代异构双卡宿主（gfx1100 架构的 RX 7900 XTX 搭配 gfx1201 架构的 RX 9070 XT）上，最初排查发现两张卡缺少 ReBAR 大窗口映射导致硬件 P2P 不可用；在主板开启 ReBAR 重启后，平台层其实已经打通——绕过 RCCL 直接跑裸 P2P DMA 拷贝（`p2p_forensic_local.py`，存档于 `results/p2p_forensic_local.json`），两张卡之间 `p2p_0_1` 与 `p2p_1_0` 均为真，16 MB 显存直拷实测达到 **$13.22\text{ GB/s}$（GPU 0 $\to$ GPU 1）和 $12.91\text{ GB/s}$（GPU 1 $\to$ GPU 0）**，且数据校验全部通过。然而，一旦换用双进程 RCCL 执行集合通信，无论切换 4 种传输通道配置，单进程（1 rank）虽全部正常，双进程跨卡 kernel 却始终在首个 All-Reduce 处互等死锁。

面对这种软件栈或异构卡对的底层死锁，正确的处理方式是：
1. **如实记录 PCIe 2-hop 层的引擎口径为 `not_covered`**，附上裸 P2P 走通与多通道死锁的对照证据，定位问题在通信库跨卡同步而非物理链路；
2. **明确引擎口径是互联层相关的**——虽然我们在 V100 双卡宿主上成功闭合了 **NVLink 层**的引擎口径（$\mathrm{BW}_{\mathrm{eff}} = 102.24\text{ GB/s}$，且 $2.94\times$ 差距完全分解闭合），但 NVLink 的拟合参数绝不能回代到 PCIe 2-hop 路径上。

把这三个口径放在一起，就构成了一套完整的通信性能定位框架：**公式口径给出脱离具体实现的物理上界，设备口径量出单卡裸通路的实际边界，引擎口径则是真实多卡集合通信的最终标尺**。做集群规划或算法选型时，先用公式口径快速筛掉跨机 TP 这种量级上就不成立的方案；真正落到特定机型调优时，再针对目标互联层实测拟合 $\alpha_{\mathrm{eff}}$ 与 $\mathrm{BW}_{\mathrm{eff}}$，用留出点检验外推误差，才能避免把纸面带宽当成线上性能。

## 练习

1. **物理链路有效带宽换算**：PCIe 5.0 $\times 16$ 单通道信号速率为 $32\text{ GT/s}$，仍采用 $128\mathrm{b}/130\mathrm{b}$ 编码。请计算其单向原始线速（raw，按十进制 $\text{GB/s}$ 计）；若实际有效带宽系数为 $75\%$，它与一条单口 $400\text{ Gbps}$ RoCEv2 链路（有效系数 $88\%$）相比，有效带宽相差多少倍？

::: details 参考答案
PCIe 5.0 $\times 16$ 的原始比特率为 $32 \times 16 = 512\text{ Gbps}$，扣除 $128\mathrm{b}/130\mathrm{b}$ 编码并换算为字节速率：

$$
\mathrm{BW}_{\mathrm{raw,PCIe5}} = \frac{512 \times 10^9}{8} \times \frac{128}{130} \approx 63.02\text{ GB/s}.
$$

乘以 $75\%$ 有效系数，得有效带宽约 $63.02 \times 0.75 \approx 47.26\text{ GB/s}$。

$400\text{ Gbps}$ RoCEv2 的原始字节速率为 $400 / 8 = 50\text{ GB/s}$，乘以 $88\%$ 有效系数得 $50 \times 0.88 = 44.00\text{ GB/s}$。

两者有效带宽之比为 $47.26 / 44.00 \approx 1.07\times$。这说明单口 400G 网卡的跨节点带宽已基本追平单条 PCIe 5.0 $\times 16$ 总线，但与同代节点内专用互联（如 NVLink4/5 的 450–900 GB/s）相比仍差一个数量级。
:::

2. **Ring-AllReduce 流量与 `algbw`/`busbw` 换算**：$P = 8$ 张 GPU 对一个 $D = 64\text{ MB}$（二进制，$64 \times 2^{20}\text{ B}$）的张量执行 Ring-AllReduce。请计算：(a) Reduce-Scatter 和 All-Gather 各需要几步、每步每张卡发送多少 MB；(b) 整次操作每张卡累计发送多少 MB；(c) 若实测总耗时 $t = 0.8\text{ ms}$，对应的算法带宽 `algbw` 与总线带宽 `busbw` 各是多少 $\text{GB/s}$（十进制）？

::: details 参考答案
(a) Reduce-Scatter 与 All-Gather 各需 $P - 1 = 7$ 步。每张卡把 64 MB 均分为 8 块，每步每张卡发送 $64 / 8 = 8\text{ MB}$。

(b) 两趟合计每张卡发送 $2 \times 7 \times 8 = 112\text{ MB}$（等价于 $2 \cdot \frac{7}{8} \times 64 = 112\text{ MB}$）。

(c) 逻辑张量字节数为 $D = 64 \times 2^{20} = 67{,}108{,}864\text{ B}$。代入 $t = 0.8 \times 10^{-3}\text{ s}$：

$$
\mathrm{algbw} = \frac{67{,}108{,}864}{0.8 \times 10^{-3} \times 10^9} \approx 83.89\text{ GB/s},
$$

$$
\mathrm{busbw} = 2 \cdot \frac{P - 1}{P} \cdot \mathrm{algbw} = 1.75 \times 83.89 \approx 146.80\text{ GB/s}.
$$
:::

3. **拐点计算与主导区判定**：某节点内互联参数为 $\alpha = 5\,\mu\text{s}$/跳、$\mathrm{BW} = 50\text{ GB/s}$。请计算 $P = 4$ 和 $P = 8$ 时的拐点 $D^*$（同时给出字节数和二进制 KB）。若在 $P = 8$ 上执行一次 $D = 2\text{ MB}$ 的 Ring-AllReduce，它落在哪个主导区？启动项占总耗时的百分比是多少？

::: details 参考答案
由 $D^* = P \cdot \alpha \cdot \mathrm{BW}$：
- $P = 4$ 时：$D^* = 4 \times (5 \times 10^{-6}) \times (50 \times 10^9) = 1{,}000{,}000\text{ B} \approx 976.56\text{ KB}$。
- $P = 8$ 时：$D^* = 8 \times (5 \times 10^{-6}) \times (50 \times 10^9) = 2{,}000{,}000\text{ B} \approx 1{,}953.13\text{ KB} \approx 1.91\text{ MB}$。

当 $P = 8$、$D = 2\text{ MB} = 2{,}097{,}152\text{ B}$ 时，$D > D^*$，刚刚进入**带宽主导区**。具体拆算两项耗时：
- 启动项：$2(8 - 1) \times 5\,\mu\text{s} = 70.00\,\mu\text{s}$。
- 带宽项：$2 \cdot \frac{7}{8} \times \frac{2{,}097{,}152}{50 \times 10^9} \approx 73.40\,\mu\text{s}$。

总耗时约 $143.40\,\mu\text{s}$，启动项占比为 $70.00 / 143.40 \approx 48.8\%$。可见在拐点附近，延迟与带宽几乎各占一半，任何单边优化都不能忽视另一项。
:::

4. **专用链路加速比区间验证**：在 $P = 2$ 下，比较链路 A（$\alpha = 1\,\mu\text{s}, \mathrm{BW} = 300\text{ GB/s}$）与链路 B（$\alpha = 2\,\mu\text{s}, \mathrm{BW} = 25\text{ GB/s}$）的 Ring-AllReduce 耗时。分别计算 $D = 4\text{ KB}$ 与 $D = 64\text{ MB}$ 时链路 A 相对链路 B 的加速比，并解释为何 $4\text{ KB}$ 处的加速比远低于两者带宽之比 $12\times$。

::: details 参考答案
在 $P = 2$ 时，$T_{\mathrm{AR}}(D) = 2\alpha + D/\mathrm{BW}$。
- $D = 4\text{ KB} = 4{,}096\text{ B}$：
  - $T_A = 2 + \frac{4{,}096}{300 \times 10^9} \times 10^6 \approx 2.0137\,\mu\text{s}$，
  - $T_B = 4 + \frac{4{,}096}{25 \times 10^9} \times 10^6 \approx 4.1638\,\mu\text{s}$，
  - 加速比 $S(4\text{ KB}) = 4.1638 / 2.0137 \approx 2.068\times$。
- $D = 64\text{ MB} = 67{,}108{,}864\text{ B}$：
  - $T_A = 2 + \frac{67{,}108{,}864}{300 \times 10^9} \times 10^6 \approx 225.70\,\mu\text{s}$，
  - $T_B = 4 + \frac{67{,}108{,}864}{25 \times 10^9} \times 10^6 \approx 2{,}688.35\,\mu\text{s}$，
  - 加速比 $S(64\text{ MB}) = 2{,}688.35 / 225.70 \approx 11.911\times$。

原因在于 $4\text{ KB}$ 远小于两条链路的拐点，双方耗时几乎完全由启动项 $2\alpha$ 决定，因此加速比被锁定在 $\alpha_B / \alpha_A = 2\times$ 附近；只有当体量远超拐点进入带宽主导区（如 $64\text{ MB}$），带宽项占绝对主导，加速比才会逼近 $\mathrm{BW}_A / \mathrm{BW}_B = 12\times$。
:::

5. **张量并行通信占比与盈亏判断**：沿用 5.4 节 Qwen3-1.7B 的参数（$d_{\mathrm{model}} = 2048$，BF16，单卡名义峰值 $195\text{ TFLOPS}$，计算效率 $\eta = 0.6243$）。当批内 token 数 $N = 512$、并行度 $\mathrm{TP} = 4$ 时，分别计算 PCIe 4.0 $\times 16$（$25\text{ GB/s}, 2\,\mu\text{s}$）与 NVLink 300（$300\text{ GB/s}, 1\,\mu\text{s}$）下的单层两次 All-Reduce 通信占比，并判断是否越过 100% 盈亏线。

::: details 参考答案
先算单次 All-Reduce 消息体量与单卡计算时间：
- $D_{\mathrm{payload}} = 512 \times 2048 \times 2\text{ B} = 2{,}097{,}152\text{ B} = 2.0\text{ MB}$。
- $T_{\mathrm{comp}} = \frac{32 \times 512 \times 2048^2}{4 \times 195 \times 10^{12} \times 0.6243} = \frac{6.8719 \times 10^{10}}{4.8695 \times 10^{14}} \approx 0.1411\text{ ms}$。

再算两档拓扑下的单层两次 All-Reduce 耗时（$P = 4$ 时 $2(P-1)=6$，$2(P-1)/P=1.5$）：
- **PCIe 4.0 $\times 16$**：单次 $T_{\mathrm{AR}} = 6 \times 2\,\mu\text{s} + 1.5 \times \frac{2{,}097{,}152}{25 \times 10^9}\text{ s} = 12 + 125.83 = 137.83\,\mu\text{s} = 0.1378\text{ ms}$，两次合计 $0.2757\text{ ms}$。通信占比为 $0.2757 / 0.1411 \approx 195.3\%$，**大幅越过 100% 盈亏线**，不可行。
- **NVLink 300**：单次 $T_{\mathrm{AR}} = 6 \times 1\,\mu\text{s} + 1.5 \times \frac{2{,}097{,}152}{300 \times 10^9}\text{ s} = 6 + 10.49 = 16.49\,\mu\text{s} = 0.0165\text{ ms}$，两次合计 $0.0330\text{ ms}$。通信占比为 $0.0330 / 0.1411 \approx 23.4\%$，**远低于 100% 盈亏线**，具备良好的并行收益。
:::

6. **从真机拟合参数反推实际拐点**：5.5 节在 V100 双卡 NV6 上拟合得到的引擎口径参数为 $\alpha_{\mathrm{eff}} = 24.45\,\mu\text{s}$/跳、$\mathrm{BW}_{\mathrm{eff}} = 102.24\text{ GB/s}$（$P = 2$）。请计算该真机引擎口径下的实际拐点 $D^*$（以二进制 MB 表示），并与名义 NVLink 300 的拐点 $585.94\text{ KB}$ 对比；解释为何真机拐点大幅右移，以及为何全局线性拟合会在 16 KB 留出点出现 $+19.77\%$ 的正误差。

::: details 参考答案
代入 $P = 2$ 的拐点公式：

$$
D^*_{\mathrm{engine}} = 2 \times (24.45 \times 10^{-6}\text{ s}) \times (102.24 \times 10^9\text{ B/s}) \approx 4{,}999{,}536\text{ B} \approx 4{,}882\text{ KB} \approx 4.77\text{ MB}.
$$

与名义 NVLink 300 的 $585.94\text{ KB}$ 相比，真机引擎拐点向右移动了约 **$8.3\times$**。原因在于，虽然真机有效带宽相对名义下降了约 $2.93\times$（$300 \to 102.24\text{ GB/s}$），但引擎层的实际启动同步开销 $\alpha_{\mathrm{eff}}$ 却比名义假设高出了 $24.45\times$（$1 \to 24.45\,\mu\text{s}$），两者的乘积 $\alpha \cdot \mathrm{BW}$ 反而放大了 $24.45 / 2.93 \approx 8.3\times$。

正因实际延迟主导区一直延伸到近 5 MB，16 KB 留出点深处延迟平台底部（实测 16/64/128 KB 均为 $40.96\,\mu\text{s}$）。而全局最小二乘在 64 KB 到 128 MB 上拟合单条直线时，中大消息处的轻微非线性会被吸收进截距项，使线性截距 $2\alpha_{\mathrm{eff}} = 48.90\,\mu\text{s}$ 高于真实小消息地板 $40.96\,\mu\text{s}$，从而在 16 KB 处产生约 $+19.8\%$ 的过估计。
:::

7. **三口径混淆诊断**：某团队在一台双卡服务器上做了两项测试：先用 PyTorch CPU `gloo` 后端测得 2 进程 16 MB All-Reduce 耗时 $12\text{ ms}$，又在单卡上用锁页内存拷贝测得 H2D 带宽为 $18\text{ GB/s}$。随后该团队得出结论：“本机双卡训练的卡间有效带宽为 $18\text{ GB/s}$，且 16 MB 集合通信延迟为 $12\text{ ms}$。”请指出该结论中的两处口径混淆，并说明要严格标定这台机器的张量并行通信代价，还缺少哪一类实测。

::: details 参考答案
该结论存在两处典型的口径混淆：
1. **将行为验证当成多卡性能**：CPU `gloo` 后端走的是主机内存与本地共享内存/回环路径，完全不经过 GPU 显存和卡间互联，其 $12\text{ ms}$ 耗时只能证明集合通信语义正确，不能代表 GPU 间 All-Reduce 延迟。
2. **将 1-hop 设备口径当成多卡引擎口径**：单卡 pinned H2D 测的是“主机内存 $\to$ 单张 GPU”的 1-hop 传输上限，它既未涵盖两张 GPU 之间的实际路由（如是否经过 CPU 根复合体 2-hop 中转、是否支持 P2P），也未包含集合通信库的分片调度、跨卡同步与归约开销，因此 $18\text{ GB/s}$ 只是上界参考，不是双卡集合通信的有效带宽。

要严格标定该机器的张量并行通信代价，必须补充**双卡 GPU 通信库（NCCL/RCCL）的引擎口径实测**：在多组消息体量（覆盖延迟主导区与带宽主导区）上以预热加多次中位数协议实测 `dist.all_reduce`，用校准集拟合 $\alpha_{\mathrm{eff}}$ 与 $\mathrm{BW}_{\mathrm{eff}}$，并用独立留出点验证外推误差；若双卡通信库无法完成测试，则应如实记录为未覆盖并保留诊断证据，而非用其他口径替代。
:::
