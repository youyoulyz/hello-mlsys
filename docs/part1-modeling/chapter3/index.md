# 第 3 章 显存占用估算：模型权重与 KV Cache

## 本章导读

> 第 1 章和第 2 章讨论的是推理速度：给定模型与硬件，生成每个 token 需要多少毫秒。把模型真正部署到服务器上之前，还要先回答一个更靠前的容量问题：一张显存有限的 GPU 究竟能不能装下目标模型？装下权重之后，剩下的显存又够同时服务多少条并发请求、支持多长的上下文？
>
> 3.1 把 GPU 显存拆成静态权重、每 token 键值缓存（KV Cache）和运行时开销三本账，并理清公式、框架分配器与设备驱动三种测量口径各自看见了什么。3.2 把三本账合成为容量可行域，推导出最大并发数与最大上下文长度之间的兑换关系，以及升级显存档位带来的非线性收益。3.3 在 RX 9070 XT 上依次检验权重、KV 缓存、预填充激活峰值、分配器碎片代理以及 vLLM 预分配池在饱和前后的真实表现。3.4 把实测中出现的每一笔残差逐字节归因到具体机制，并完成解析模拟器与 vLLM 实测 KV 池的闭合对账。章末实验与练习提供完整脚本命令与离线存档。

## 教学目标

- 能根据模型结构参数逐层计算静态权重参数量与显存占用，并说明权重共享（`tie_word_embeddings`）与数值精度对容量的影响。
- 能写出分组查询注意力（GQA）口径下每 token 的 KV 缓存字节数公式，并解释 GQA 相对多头注意力（MHA）的显存节省倍数。
- 能区分公式口径、PyTorch 分配器口径（`allocated` / `reserved`）与设备驱动口径（`rocm-smi`）的观测范围，说明激活工作区与分配器碎片的来源。
- 能根据显存预算手算最大上下文 $S_{\max}(B)$ 与最大并发 $B_{\max}(S)$，并解释 vLLM 预分配池满载时的排队与容量边界行为。
- 能将解析账本与真机实测逐项对账，把残差准确归因到运行时上下文、Python 引用环、分配器块对齐取整或引擎预留开销。

## 3.1 显存的三本账

估算一张 GPU 的显存容量，很像规划一间固定面积的仓库。仓库里第一块地要常年摆放大件固定设备，设备一进场就不再挪窝；第二块地按每天进出的订单动态摆放周转货箱，订单越多、每笔订单越长，占用的货架就越多；角落里还得留出通道、装卸区和未能凑整的零散空位。如果只盯着设备本身的面积，忽略周转货箱和装卸通道，仓库一开工就会爆仓。

推理过程中的 GPU 显存占用同样可以按生命周期分成三本账：模型加载后常驻不变的**静态权重**、随请求并发数与上下文长度动态增减的 **KV 缓存**，以及张量之外的**运行时开销**。用一套统一符号把三本账写下来：

$$
\begin{aligned}
M_{\mathrm{weights}} &= N_{\mathrm{params}} \times b_{\mathrm{param}}, \\
m_{\mathrm{kv}} &= 2 \times L \times H_{\mathrm{kv}} \times D_{\mathrm{head}} \times b_{\mathrm{elem}}, \\
M_{\mathrm{avail}} &= M_{\mathrm{total}} \times u - M_{\mathrm{weights}} - M_{\mathrm{overhead}}.
\end{aligned}
$$

其中，$N_{\mathrm{params}}$ 为模型参数总数，$b_{\mathrm{param}}$ 和 $b_{\mathrm{elem}}$ 分别为权重与 KV 元素的每元素字节数（BF16 下均为 2 字节），$M_{\mathrm{total}}$ 为显卡物理显存总量，$u \in (0, 1]$ 为允许推理引擎使用的显存比例。从可用预算中扣除静态权重和常驻运行时开销后，剩余的 $M_{\mathrm{avail}}$ 就决定了 KV 缓存池的容量上限。

### 3.1.1 静态权重

静态权重显存的计算公式看起来再简单不过：参数总数乘以单个参数的字节数。但到了真实部署时，第一个容易踩的坑就是把模型名称里的“0.6B”“1.7B”“4B”直接当成精确参数量。模型营销名往往是四舍五入后的近似量级，里面藏着三处足以改变几百兆甚至数吉字节显存的结构细节：一是大词表带来的嵌入层占比，二是输入词嵌入与输出分类头是否共享同一份权重（`tie_word_embeddings`），三是现代 Transformer 采用的 SwiGLU 前馈网络包含三个投影矩阵而非早期的两个，而分组查询注意力又会缩小键值投影矩阵的尺寸。

以 **Qwen3-1.7B** 为例做一次逐层手算，就能看清每个部件到底占了多少参数。查阅其配置文件可得：$L = 28$ 层，隐藏维 $d = 2048$，查询头数 $H_q = 16$，键值头数 $H_{\mathrm{kv}} = 8$，单头维度 $D_{\mathrm{head}} = 128$，中间层维 $d_{\mathrm{inter}} = 6144$，词表大小 $V = 151{,}936$，线性层无偏置项，且启用了输入输出权重共享 `tie_word_embeddings=true`。令 $d_q = H_q D_{\mathrm{head}} = 2048$、$d_{\mathrm{kv}} = H_{\mathrm{kv}} D_{\mathrm{head}} = 1024$，单个 Transformer 层的参数分解如下：

| 层内组件 | 参数量计算式 | 单层参数量 |
| --- | --- | ---: |
| `q_proj` | $d \times d_q = 2048 \times 2048$ | $4.194\;\text{M}$ |
| `k_proj` / `v_proj` | $2 \times (d \times d_{\mathrm{kv}}) = 2 \times 2048 \times 1024$ | $4.194\;\text{M}$ |
| `o_proj` | $d_q \times d = 2048 \times 2048$ | $4.194\;\text{M}$ |
| MLP（`gate` / `up` / `down`） | $3 \times d \times d_{\mathrm{inter}} = 3 \times 2048 \times 6144$ | $37.749\;\text{M}$ |
| `q_norm` / `k_norm` 与层归一化 | $d_q + d_{\mathrm{kv}} + 2d$ | $0.007\;\text{M}$ |
| **单层合计** | — | **$50.34\;\text{M}$** |

把 28 层加起来共约 $1{,}409.5\;\text{M}$ 参数，再加上全局词嵌入矩阵（$V \times d = 151{,}936 \times 2048 \approx 311.16\;\text{M}$）和末层归一化，总参数量为：

$$
N_{\mathrm{params}} = 311.16\;\text{M} + 28 \times 50.34\;\text{M} = 1{,}720.7\;\text{M}.
$$

这个手算结果直接点出了现代中小语言模型的两个结构特点。第一，单层内部的参数大头并不在注意力，而在前馈网络（MLP）——SwiGLU 结构包含 `gate`、`up`、`down` 三个大型投影矩阵，且中间层维度达到隐藏维的三倍（$d_{\mathrm{inter}} = 3d = 6144$），单是 MLP 就占了每层 50.34M 参数里的 37.75M，整整四分之三；而采用分组查询注意力（GQA）后，`k_proj` 和 `v_proj` 的宽度减半，让整个注意力模块的四个投影矩阵合计只占不到四分之一。第二，15 万词表的词嵌入矩阵单独就占了 311.16M 参数，接近整张 1.7B 模型的五分之一。因为 Qwen3-0.6B、Qwen3-1.7B 和 Qwen3-4B 均启用了 `tie_word_embeddings=true`，输出头 `lm_head` 直接复用词嵌入矩阵的内存，不重复计数，在 1.7B 上就省下了整整 311M 参数（BF16 下约 0.577 GiB）。如果换成不共享词表权重的同类模型，这 311M 参数就得算两遍，静态权重瞬间膨胀近 18%，容量账本很容易从第一步就漏算半个多 GiB。

在 BF16（每参数 2 字节）下，Qwen3-1.7B 的静态权重显存为 $1{,}720.7 \times 10^6 \times 2 / 2^{30} \approx 3.205\;\text{GiB}$。改变数值精度会等比例缩放权重显存，它往往是决定模型能不能装进目标显卡的第一道硬门槛；同时要注意，权重精度与 KV 缓存精度在推理引擎中可以分开指定（例如常见的 W4A16 方案把权重压到 4 比特，而 KV 缓存仍保持 BF16）：

| 权重精度 | 每参数字节数 | Qwen3-1.7B 权重 | Qwen3-4B 权重 |
| --- | ---: | ---: | ---: |
| FP32 | $4$ | $6.410\;\text{GiB}$ | $14.985\;\text{GiB}$ |
| **BF16（本章主线）** | **$2$** | **$3.205\;\text{GiB}$** | **$7.493\;\text{GiB}$** |
| FP8 / INT8 | $1$ | $1.603\;\text{GiB}$ | $3.746\;\text{GiB}$ |
| INT4 | $0.5$ | $0.801\;\text{GiB}$ | $1.873\;\text{GiB}$ |

以 15.9 GiB 显存的 RX 9070 XT 为参照：如果用 FP32 加载 Qwen3-4B，单是权重就要吃掉 14.99 GiB，几乎把整张卡填死，根本留不出空间给上下文缓存和运行激活；降到 BF16 后权重缩减至 7.493 GiB，才腾出了可观的运行余量；若进一步量化到 INT4，4B 权重仅占 1.873 GiB。因此，数值精度首先是容量准入门槛，具体的量化算法与精度损失权衡将在[第 4 章](/part1-modeling/chapter4/)展开。

### 3.1.2 每 token 的键值缓存（KV Cache）

自回归解码每生成一个新 token，都必须让它与之前所有历史 token 计算注意力权重并加权求和。如果不保存任何中间结果，生成第 1,000 个 token 时，引擎就得把前 999 个历史 token 重新送进线性投影层算一遍键（Key）和值（Value），计算量会随生成长度平方级膨胀。为了避免这种重复劳动，推理引擎把每个已处理 token 的 K、V 向量缓存在显存里，后续每一步只需给新来的 1 个 token 算出 K、V 并追加到末尾，其余历史全部直接读取——本质上是用显存空间换取计算时间的记忆化（memoization）。[Pope et al. (2022)](https://arxiv.org/abs/2211.05102)

要算清每多保存 1 个 token 究竟要花多少字节，可以用一个读书小组的画面来想象**分组查询注意力（GQA）**相对**标准多头注意力（MHA）**省在哪里。假设一间教室里有 16 位读者（查询头 $H_q = 16$）一起读一本长书，每读完一页（1 个 token），都需要留下笔记供后面翻查。在标准 MHA 模式下，16 位读者各自记一套私人的 K、V 笔记，每读一页就得往书架上存 16 份笔记。到了 GQA 模式下，16 位读者分成 8 个两人小组，每组共用 1 套公用的 K、V 笔记（键值头 $H_{\mathrm{kv}} = 8$），于是每读完一页只需要往书架上存 8 份笔记，书架占用瞬间减半。如果像 Qwen3-4B 那样 32 位读者分成 8 个四人小组（32q/8kv），书架占用就直接缩小到原来的四分之一。

回到精确公式：每个 token 穿过 $L$ 层 Transformer 时，需要在每一层存入 $H_{\mathrm{kv}}$ 个键向量和 $H_{\mathrm{kv}}$ 个值向量，每个向量长度为 $D_{\mathrm{head}}$，每个元素占 $b_{\mathrm{elem}}$ 字节。把这些因子连乘，就得到每增加 1 个 token 所需的 KV 缓存字节数：

$$
m_{\mathrm{kv}} = 2 \times L \times H_{\mathrm{kv}} \times D_{\mathrm{head}} \times b_{\mathrm{elem}}.
$$

代入 BF16（$b_{\mathrm{elem}} = 2$ 字节）与 Qwen3 系列的结构参数，可以立刻算出三款模型的精确单价：

- **Qwen3-0.6B / Qwen3-1.7B**（$L = 28, H_{\mathrm{kv}} = 8, D_{\mathrm{head}} = 128$）：$2 \times 28 \times 8 \times 128 \times 2 = 114{,}688\;\text{B} = 112\;\text{KiB/token}$。
- **Qwen3-4B**（$L = 36, H_{\mathrm{kv}} = 8, D_{\mathrm{head}} = 128$）：$2 \times 36 \times 8 \times 128 \times 2 = 147{,}456\;\text{B} = 144\;\text{KiB/token}$。

把 112 KiB/token 放进真实业务对话里算一笔账，就能立刻感受到 KV 缓存的威力。假设一个在线问答服务运行 Qwen3-1.7B，每条请求平均输入 4,096 个提示词 token、生成 1,024 个回答 token，总长度 5,120 token。单条请求占用的 KV 缓存就是 $5{,}120 \times 112\;\text{KiB} = 573{,}440\;\text{KiB} = 560\;\text{MiB}$。乍看之下不过半个 GiB，可只要同时有 10 位用户在线并发，KV 缓存总占用就会立刻冲到 **5.47 GiB**——已经反超了整张 1.7B 模型 3.205 GiB 的静态权重！在长上下文或高并发部署里，真正吃光显存的往往不是模型权重本身，而是成百上千条并发序列累积起来的 KV 缓存。

仔细端详这个公式，可以直接提炼出 KV 缓存的四条核心规律。第一，单条序列的 KV 显存 $m_{\mathrm{kv}} \cdot S$ 随序列长度 $S$ **严格线性增长**——常听到的注意力 $O(S^2)$ 复杂度指的是计算量，而不是持久化缓存的显存占用。第二，公式中只出现层数 $L$、键值头数 $H_{\mathrm{kv}}$ 和单头维度 $D_{\mathrm{head}}$，完全不出现隐藏维 $d$、中间层维度 $d_{\mathrm{inter}}$ 和查询头数 $H_q$；因此参数量相差近三倍的 Qwen3-0.6B 与 Qwen3-1.7B，每多存 1 个 token 的缓存单价竟然完全相同，都是 112 KiB。第三，解码阶段每生成一个 token 就在末尾追加 1 行，且在整条请求彻底结束前，历史行都不能释放，因此单条请求的显存占用随生成进度单调攀升。第四，预填充阶段需要一口气写入全部输入 token 的 KV 缓存，同时叠加整段序列的前向中间激活，往往形成单次推理最危险的瞬态显存尖峰。

### 3.1.3 运行时开销的三种来源

如果只把静态权重和 KV 缓存加在一起，去和显卡物理显存作比较，上线后依然会频频撞上显存溢出（OOM）。因为在显式张量之外，还有三笔真实存在的运行时开销占据着显存。

第一笔是**驱动与运行时上下文**。只要进程初始化了 PyTorch 或推理引擎的 GPU 运行环境，驱动与运行时库就必须把指令队列、内核代码页和基础状态常驻在显存里。这笔开销类似仓库里的配电房和管理间，不管你加载的是 0.6B 的小模型还是 70B 的大模型，只要进程一启动，这几百兆显存就已经被扣走了。

第二笔是**激活工作区（activation workspace）**。前向计算并不是一步到位地把输入变成输出，每一层矩阵乘的临时结果、归一化的中间向量以及注意力计算时的临时缓冲区，都需要显存来临时落脚。对于单步解码，每次只处理 1 个 token，形状为 $1 \times d_{\mathrm{inter}}$ 的中间激活只有几十 KiB；但遇到长达 4,096 甚至 8,192 个 token 的预填充时，MLP 内部形状为 $S \times d_{\mathrm{inter}}$ 的中间张量、以及输入输出 logits 矩阵（$S \times V$，在 15 万词表下尤其可观）会同时存活，拉起一个高达吉字节级的瞬态尖峰（如果注意力没有走 FlashAttention 融合核，甚至还会额外物化出 $O(H_q S^2)$ 的巨大分数矩阵）。这笔空间在步末就会释放，不留在稳态账本里，但它决定了预填充那一瞬间显卡会不会直接崩掉。

第三笔是**分配器碎片（fragmentation）**。为了避免每次创建和销毁小张量都向操作系统发起昂贵的显存系统调用，PyTorch 等框架内置了缓存分配器（caching allocator）：它先向驱动一次性批发大块显存放进自己的私有池，再按需切小块分给张量。碎片按产生位置又分两种：**内碎片**是分配器为了便于复用，把张量请求尺寸向上取整到标准块档位而留下的块内空隙（3.4 节会精确测出它在 4B 模型上累积出的字节数）；**外碎片**则是反复申请和释放不同尺寸张量后，退回私有池但尚未合并归还给操作系统的零散空闲块，从设备外部看依然显示为“已占用”。

### 3.1.4 公式、分配器与驱动三个测量口径

排查显存问题时，新手最常困惑的一幕是：明明按公式算模型权重只有 3.2 GiB，`torch.cuda.memory_allocated()` 也显示 3.2 GiB，可敲一下 `rocm-smi` 或 `nvidia-smi` 却看到显存已经用掉了 4.6 GiB。三个工具给出的数字各不相同，并不是谁测坏了，而是它们站在三个同心圆的不同层级上观察同一块物理显存。

不妨把显卡显存比作一栋物流大楼。**公式口径**只清点货物本身的净体积（$N_{\mathrm{params}} b_{\mathrm{param}}$ 与 $m_{\mathrm{kv}} S$），既不算货架包装也不算通道，它是容量规划的理论下界。**PyTorch 分配器口径**提供两个读数：`memory_allocated()` 看的是当前摆着有效货物的货架总面积（存活张量占用的块之和，包含块对齐包装）；`memory_reserved()` 看的是框架从大楼里整租下来的全部库区面积，里面既包括摆着货的货架，也包括暂时空着、留给下次复用的空闲库位。最外层的**设备驱动口径**（`rocm-smi --showmeminfo vram` 或 `amdsmi`）则是大楼物业的总账，它看到的面积等于驱动与运行时上下文（配电房）、框架整租的 `reserved` 库区，再加上所有非 PyTorch 进程占用之和。

| 测量口径 | 读取方式 | 观测对象与定位 |
| --- | --- | --- |
| 公式口径 | $N_{\mathrm{params}} b_{\mathrm{param}}$，$m_{\mathrm{kv}} S$ | 仅计张量净字节数，作为容量规划的理论下界 |
| 框架分配器口径 | `torch.cuda.memory_allocated()` / `memory_reserved()` | 分别反映存活张量总占用与分配器从设备保留的显存池总量（含空闲块） |
| 设备驱动口径 | `rocm-smi --showmeminfo vram`（或 `amdsmi`） | 驱动视角的总已用显存，等于运行时上下文、分配器保留池与非 PyTorch 占用之和 |

用一段极简的张量生命周期走一遍，就能彻底记住这三个口径的联动方式。假设 PyTorch 初始化完 GPU 上下文后，设备底噪是 250 MiB。第一步，创建一个净大小 100 MiB 的张量 `x`：此时公式口径为 100 MiB，`allocated` 变为 100 MiB，`reserved` 也向驱动申请了 100 MiB（或按块取整略多一点），而 `rocm-smi` 读数变为 $250 + 100 = 350\;\text{MiB}$。第二步，执行 `del x` 但不调用清理接口：此时公式口径和 `allocated` 立刻归零，但缓存分配器把这块 100 MiB 留在私有池里等待下次复用，所以 `reserved` 依然停在 100 MiB，`rocm-smi` 也纹丝不动地停在 350 MiB——这就是为什么很多初学者删完张量却发现 `rocm-smi` 没降、误以为发生了显存泄露。第三步，再调用 `torch.cuda.empty_cache()`：私有池把空闲块退还给驱动，此时 `reserved` 归零，`rocm-smi` 才回落到 250 MiB。

理清这三层嵌套关系后，就能准确使用每一套数字：做部署前的纸面规划时，用公式口径加上一笔固定预留项 $M_{\mathrm{overhead}}$（例如先取 0.5 GiB 近似常驻运行时开销）来快速估算上限；做代码级显存泄露排查时，对照 `allocated` 和 `reserved` 的差值；而判断是否逼近硬件物理红线，则必须以设备驱动口径为准。3.3 与 3.4 节将在真机上逐一核对这三层口径的闭合关系。

## 3.2 容量可行域：并发与上下文的兑换

### 同一块显存池的两种切法

把 3.1 节的三本账拼在一起，剩余可用显存 $M_{\mathrm{avail}}$ 就像一块面积已经划定的停车场，而 $m_{\mathrm{kv}}$ 是每个 token 车位的固定占地面积。把总面积除以单个车位面积并向下取整，就得到这张显卡最多能同时停放的 KV token 总量，记为池总容量 $T_{\mathrm{pool}} = \lfloor M_{\mathrm{avail}} / m_{\mathrm{kv}} \rfloor$。

这块池子一旦固定，并发请求数 $B$ 和每条请求的上下文长度 $S$ 就变成了同一块显存池的两种切法：想同时接待更多用户，每人能分到的上下文配额就得缩短；想支持超长文档对话，能同时放进来的并发用户数就必须减少。两者满足一对互为反函数的约束关系：

$$
S_{\max}(B) = \left\lfloor \frac{M_{\mathrm{avail}}}{B \cdot m_{\mathrm{kv}}} \right\rfloor,
\qquad
B_{\max}(S) = \left\lfloor \frac{M_{\mathrm{avail}}}{S \cdot m_{\mathrm{kv}}} \right\rfloor.
$$

以 **RX 9070 XT**（15.9 GiB 物理显存，取 $u = 0.9$ 即 14.31 GiB 预算，固定预留 $M_{\mathrm{overhead}} = 0.5\;\text{GiB}$，BF16 口径）为例，解析账本模块 `mem_ledger.py` 直接读取三款 Qwen3 模型的配置文件，算出对应的容量可行域：

| 模型 | 参数量 $N_{\mathrm{params}}$ | 权重 $M_{\mathrm{weights}}$ | $m_{\mathrm{kv}}$ | 可用 KV 池 $M_{\mathrm{avail}}$ | 池容量（token） | $B_{\max}$（$S=2048/4096/8192$） | $S_{\max}$（$B=1/4/16$） |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| Qwen3-0.6B | $596.1\;\text{M}$ | $1.110\;\text{GiB}$ | $112\;\text{KiB}$ | $12.700\;\text{GiB}$ | $118{,}897$ | $58\;/\;29\;/\;14$ | $118{,}897\;/\;29{,}724\;/\;7{,}431$ |
| Qwen3-1.7B | $1{,}720.7\;\text{M}$ | $3.205\;\text{GiB}$ | $112\;\text{KiB}$ | $10.605\;\text{GiB}$ | $99{,}287$ | $48\;/\;24\;/\;12$ | $99{,}287\;/\;24{,}821\;/\;6{,}205$ |
| Qwen3-4B | $4{,}022.6\;\text{M}$ | $7.493\;\text{GiB}$ | $144\;\text{KiB}$ | $6.317\;\text{GiB}$ | $46{,}000$ | $22\;/\;11\;/\;5$ | $46{,}000\;/\;11{,}500\;/\;2{,}875$ |

用 3.1 节的手算数字核对 Qwen3-1.7B 这一行，每一步都能直接验算：总预算 $15.9 \times 0.9 = 14.31\;\text{GiB}$，扣掉权重 3.205 GiB 和固定预留 0.5 GiB，剩下 $M_{\mathrm{avail}} = 10.605\;\text{GiB}$；换算成 KiB 再除以 $112\;\text{KiB/token}$，得到 $10.605 \times 1024^2 / 112 \approx 99{,}287\;\text{tokens}$。这 99,287 个 token 车位，在短对话场景（每条 2,048 token）下能同时接待 $\lfloor 99{,}287 / 2{,}048 \rfloor = 48$ 位用户；切到中等对话（4,096 token）时降为 24 条并发；如果业务改成 16,384 token 的长文档问答，同一块池子就只能切成 $\lfloor 99{,}287 / 16{,}384 \rfloor = 6$ 条并发（32K 场景下仅剩 3 条）。

同样地，调整显存利用率参数 $u$ 也会直接增减这块池子。例如在 RX 9070 XT 上把 $u$ 从 0.8 提高到 0.9，多出来的 $0.1 \times 15.9 = 1.59\;\text{GiB}$ 预算不需要再分给已经装好的模型权重，而是 100% 全部注入 KV 缓存池——在 3.3.3 节的 Qwen3-4B 实测里，仅把 `util` 从 0.8 调到 0.9，KV 池就从 4.03 GiB 跃升至 5.62 GiB，单这一项微调就换来了近 40% 的并发容量增益。正是这种共享池子的硬约束，构成了[第 7 章](/part1-modeling/chapter7/)连续批处理按缓存块接纳请求、以及[第 8 章](/part1-modeling/chapter8/) PagedAttention 消除块内浪费的物理前提。

![RX 9070 XT 显存可行域堆叠图：对比 Qwen3-0.6B、1.7B 和 4B 的静态权重、固定预留与剩余 KV 池占比。模型越大，权重挤占越多，可供 KV 缓存使用的池子越小。](./images/fig1-ledger.png)

### 模型规模与显存档位的非线性杠杆

顺着上表从 0.6B 往下读到 4B，可以看到显存容量上的第一条强挤压效应：**在同一张显卡上，模型越大，留给并发与上下文的空间被双重压缩。** 在 14.31 GiB 的预算里，Qwen3-0.6B 的权重只占 7.8%，足足留出 12.70 GiB（11.9 万 token）给 KV 池；可换上 Qwen3-4B 后，静态权重一口气吃掉了 52.4% 的预算，剩余显存砍半到 6.317 GiB，与此同时层数从 28 层增至 36 层，让每 token KV 单价从 112 KiB 涨到了 144 KiB。分子变小、分母变大，双重挤压之下，KV 池容量直接缩水到 46,000 token，4,096 上下文下的最大并发从 29 条骤降到 11 条。

反过来，如果把同一批模型搬到更大显存的显卡上，会出现极强的**正向非线性杠杆**。把显卡升级为 48 GB 显存档（以下按 48 GiB 标称容量与同样的 $u = 0.9, M_{\mathrm{overhead}} = 0.5\;\text{GiB}$ 做解析估算，未上真机实测），静态权重并不会随显卡变大而膨胀，超出权重门槛之后的新增显存几乎 100% 全部灌进了 KV 缓存池：

| 模型 | 权重 $M_{\mathrm{weights}}$ | 48 GB 档可用池 $M_{\mathrm{avail}}$ | 池容量（token） | $B_{\max}$（$S=4096 / 8192$） |
| --- | ---: | ---: | ---: | ---: |
| Qwen3-0.6B | $1.110\;\text{GiB}$ | $41.590\;\text{GiB}$ | $389{,}373$ | $95\;/\;47$ |
| Qwen3-1.7B | $3.205\;\text{GiB}$ | $39.495\;\text{GiB}$ | $369{,}763$ | $90\;/\;45$ |
| Qwen3-4B | $7.493\;\text{GiB}$ | $35.207\;\text{GiB}$ | $256{,}371$ | $62\;/\;31$ |

同样运行 Qwen3-4B，显卡物理显存从 15.9 GiB 升到 48 GiB 只增大了约 3 倍，可用 KV 池却从 46,000 token 跃升至 256,371 token，足足翻了 **5.6 倍**，$B_{\max}(4096)$ 从 11 条拉升到 62 条。理解这一杠杆有助于做硬件选型：当模型权重已经占据单卡显存的一半以上时，哪怕只多出一点显存空间（或者通过权重量化把静态门槛压低一半），换来的并发与上下文增长都远大于显存增幅本身。

## 3.3 真机三口径对账与 vLLM 显存管理

建立好纸面账本之后，需要在真实硬件和生产级推理引擎上逐项核对。本节在 **RX 9070 XT**（15.92 GiB，PyTorch + ROCm BF16 环境，以及 `vllm 0.29.0` 容器）上依次检验静态权重、KV 缓存、瞬态激活峰值、碎片代理，以及 vLLM 预分配池在满载前后的运行行为。

### 3.3.1 上下文底噪与静态权重对账

测量模型净显存前，先要摸清驱动与运行时上下文的固定底噪（数据见 `results/mem_real_9070xt.json`）。显卡上没有任何计算进程时，`rocm-smi` 的空闲读数为 **0.0559 GiB**；初始化 PyTorch GPU 上下文并创建一个极小张量后，`rocm-smi` 读数立刻跳升至 **0.2519 GiB**，而此时 `torch allocated = 0.0 GiB`、`reserved = 0.002 GiB`。两者之差 **+0.196 GiB** 就是 PyTorch GPU 运行时上下文的固定入场费，与后面加载什么模型无关。

**预填充瞬态激活峰值**则暴露了稳态账本之外的“隐形尖峰”。在 Qwen3-1.7B 上执行一次 $S = 4096$ 的真实预填充（开启 `use_cache=True`），同时记录前向结束后的稳态显存与前向过程中的 `max_memory_allocated`：前向结束后稳态显存为 **3.6428 GiB**，正好等于静态权重 3.2053 GiB 加上 4,096 token 的 KV 缓存 0.4375 GiB；然而在前向计算进行到一半时，瞬态显存峰值曾冲高到 **4.8968 GiB**。两者的差值 **1.2539 GiB** 就是本次 4,096-token 完整预填充撑出来的激活工作区。虽然它在前向结束、临时输出释放后立刻归零，但假如显卡在预填充前只剩下 1.0 GiB 空闲显存，就算稳态账本算下来绰绰有余，程序依然会在预填充瞬间崩溃。

**分配器碎片上界**用来衡量外碎片究竟有多大。清空缓存后，在显存里连续执行 30 轮不同形状张量的申请与释放，最后释放全部存活张量。此时 `torch allocated = 0.0000 GiB`，但 `torch reserved = 0.1484 GiB`，设备驱动读数 `rocm-smi used = 0.2043 GiB`（恰好等于空卡底噪 0.0559 GiB 加上分配器保留的 0.1484 GiB）。这 0.1484 GiB 就是框架分配器留在私有池里、尚未归还给驱动的空闲块总和，它构成了本测试下外碎片的上界——相比数吉字节的模型权重和 KV 缓存，它的量级小得多。

### 3.3.3 vLLM 启动预分配与 KV 池饱和行为

裸 PyTorch 在推理时随用随申请、用完再释放；而生产级推理引擎 **vLLM** 采取了截然不同的**启动时预分配**策略：引擎启动时先加载模型权重，紧接着用一次按 `max_num_batched_tokens` 满额构造的模拟前向（profiling run）测出该批处理预算下最坏情况的激活工作区峰值，并把这部分空间从预算里提前锁死，最后把 `gpu_memory_utilization` 划定的预算内所有剩余显存一次性全部划归为 KV 缓存池。这样做的好处非常直接：只要启动阶段的模拟前向没爆显存，线上正式接客后无论并发多高，引擎都只在自己管辖的缓存池里按固定块大小（例如每块 16 个 token）做页表式分配，既不会再向操作系统做大块设备显存申请，也不会在预填充瞬间突然因为激活尖峰而触发显存溢出。[Kwon et al. (2023)](https://arxiv.org/abs/2309.06180)

![vLLM 启动显存四项分账图：展示权重、非权重常驻开销、激活峰值与预分配 KV 池之和严格贴合 gpu_memory_utilization 设定的显存预算。](./images/fig3-vllm-ledger.png)

表中每一行的四项加起来都严格等于目标预算：$\text{目标预算} = (\text{权重} + \text{非权重常驻}) + \text{激活峰值} + \text{KV 池}$。以 Qwen3-4B 的 `util=0.9` 为例，$(7.56 + 0.55) + 0.60 + 5.62 = 14.33\;\text{GiB}$，而启动完毕后 `rocm-smi` 读出的设备已用显存正是 14.3311 GiB，账本完全贴合。

对比三组不同 `max_model_len` 的行，可以纠正工程中两个极其常见的误解。第一，**KV 池容量由物理显存和 `gpu_memory_utilization` 决定，根本不随 `max_model_len` 改变**。无论把 `max_model_len` 设为 4,096、8,192 还是 16,384，4B 在 `util=0.9` 下分到的 KV 池都纹丝不动地停在 40,928 token。调小 `max_model_len` 并不会给 KV 池腾出哪怕 1 字节的显存，它只是把单条请求允许的最长长度切短了，于是日志里按最坏满额估算出来的名义并发上限恰好成倍翻番（$40{,}928 / 16{,}384 = 2.50\times \to 5.00\times \to 9.99\times$）。第二，**激活预留取决于分块预填充的每步 token 预算**。vLLM 在默认分块预算（`max_num_batched_tokens=8192`）与融合算子路径下测出 1.7B 的激活峰值为 0.41 GiB（4B 为 0.60 GiB），它和 3.3.2 节裸 PyTorch 单发 4,096-token 完整预填充测出的 1.2539 GiB 属于不同执行路径与不同口径，不能直接相减并宣称“省下了 0.84 GiB 稳态显存”。

::: details 工程备注：在 16 GiB 显卡上串行探测多个 vLLM 实例

在 vLLM 0.29 中，`EngineCore` 运行于独立子进程，其启动日志直接写入继承的标准输出/错误文件描述符，因此探测脚本在文件描述符层对日志进行分流记录。同时，仅在 Python 中 `del llm` 并触发垃圾回收不会立即终止 `EngineCore` 子进程（显存仍会被占据超过 12 GiB），必须显式调用 `llm.llm_engine.engine_core.shutdown()` 并等待设备显存回落至 1 GiB 以下后再启动下一组配置。

:::

当在线并发请求的总缓存需求超过预分配的 KV 池时，服务会发生什么？是直接报显存溢出，还是把正在生成的老请求踢出去（抢占）？把 Qwen3-4B（`util=0.9`, `max_model_len=8192`，KV 池容量 40,928 token）当作一家只有固定座位的餐厅，就能直观理解调度器的选择。向引擎同时发送 $N \in \{2, 4, 8, 16\}$ 条请求，每条输入 4,096 token、最多输出 256 token，即单条请求满额需要 4,352 个 token 车位。用总容量除以单条需求，这家餐厅最多能同时坐下 $40{,}928 / 4{,}352 \approx 9.4$ 桌客人：

| 并发请求数 $N$ | 总 KV 需求（token） | 占池比例 | 总墙钟耗时（s） | 抢占次数 | 聚合输出吞吐（tok/s） |
| ---: | ---: | ---: | ---: | ---: | ---: |
| $2$ | $8{,}704$ | $21\%$ | $9.55$ | $0$ | $53.6$ |
| $4$ | $17{,}408$ | $42\%$ | $10.59$ | $0$ | $96.7$ |
| $8$ | $34{,}816$ | $85\%$ | $13.75$ | $0$ | $131.1$ |
| $16$ | $69{,}632$ | $170\%$ | $27.31$ | $0$ | $142.3$ |

![KV 缓存线性增长与 vLLM 并发压测图：左图展示三口径下纯 KV 显存随长度严格线性重合，右图展示并发超过 KV 池上限（170%）后总耗时翻倍、吞吐趋于平台。](./images/fig4-capacity.png)

当同时涌入 2、4、8 条请求（占池 21%–85%）时，池子装得下全部请求，所有客人都能直接入座并发生成，聚合输出吞吐从 53.6 tok/s 一路攀升到 131.1 tok/s，整批完成的总耗时也仅从 9.55 s 缓增到 13.75 s。可当并发跳升到 16 条（总需求达到池容量的 170%）时，总耗时几乎翻倍至 27.31 s，聚合吞吐则撞上平台停在 142.3 tok/s 附近，而整个过程的**抢占次数始终是 0**。

原因很简单：当第一波 9 条请求进场时，它们合计吃掉了约 $9 \times 4{,}352 = 39{,}168$ 个 token 车位，占去 40,928 token 池容量的 95.7%，剩下的 1,760 个车位不够再塞进第 10 条 4,352 token 的请求。此时，启用了分块预填充与准入检查的调度器不会把吃到一半的客人轰出去腾座，也不会直接把门外的客人拒之门外，而是暂停接纳新请求的预填充，让超出的 7 条请求老老实实留在等待队列里；等到第一波请求陆续生成完毕、释放出整批缓存块后，第二波 7 条请求再依次进场完成。于是 16 条请求自然分成了两波执行，总耗时从 13.75 s 翻倍到 27.31 s，却避免了抢占重算带来的额外浪费。这组数据也印证了另一点：日志里的“名义并发 $5.00\times$”是按每条都占满 8,192 token 算出的保守下界；实际能同时驻留多少条请求，取决于真实业务的平均请求长度（本例中每条 4,352 token，实际可驻留约 9.4 条）。

## 3.4 残差归因与模拟器对账

前面三节里出现了四套口径（公式、PyTorch 分配器、设备驱动和 vLLM 内部账本），以及几处零点零几到零点七 GiB 不等的差值。如果不把这些差值追到底，显存模型就永远留着一笔“说不清道不明的糊涂账”。本节把每一笔残差逐项归因到具体机制，让整本显存账彻底闭合。

### 设备级读数与 `reserved` 池的对应关系

先看一个在顺序加载多个模型时非常诡异的现象。把 3.3.1 节依次加载 0.6B、1.7B 和 4B 时的绝对显存读数全部摊开，并与“上下文基线 0.2519 GiB + `torch reserved`”逐行对照：

| 加载后时刻 | `torch allocated`（GiB） | `torch reserved`（GiB） | `reserved − allocated`（GiB） | `rocm-smi used`（GiB） | `0.2519 + reserved`（GiB） |
| --- | ---: | ---: | ---: | ---: | ---: |
| Qwen3-0.6B | $1.1102$ | $1.1328$ | $0.0226$ | $1.3850$ | $1.3847$（$\Delta +0.0003$） |
| Qwen3-1.7B | $3.2053$ | $4.3262$ | $1.1209$ | $4.5831$ | $4.5781$（$\Delta +0.0050$） |
| Qwen3-4B | $7.5473$ | $10.7598$ | $3.2125$ | $11.0194$ | $11.0117$（$\Delta +0.0077$） |

先核对最右侧两列：`rocm-smi used` 与 `0.2519 + reserved` 在三行上全部重合在 **$\pm 0.008\;\text{GiB}$** 以内。这用实测坐实了 3.1.4 节的层级关系——设备驱动口径看见的就是“运行时上下文 + 框架保留池”，并不关心池子里有多少张量是活的。

再把目光移到中间一列 `reserved − allocated`，一个惊人的巧合浮现出来：刚加载完 1.7B 时，多出来的 1.1209 GiB 恰好等于上一个已经删掉的模型 0.6B 的权重（1.1102 GiB + 0.0107 GiB 对齐余量）；刚加载完 4B 时，多出来的 3.2125 GiB 又恰好等于上一个模型 1.7B 的权重（3.2053 GiB + 0.0072 GiB 对齐余量）！明明代码里已经执行了 `del model`，为什么上一任模型的显存块还幽灵般地赖在 `reserved` 里不走？

罪魁祸首是 **Python 的引用环**。可以把引用环想象成两个人互相攥着对方储物柜的钥匙：外部变量 `model` 只是贴在门上的名字牌。执行 `del model` 撕掉了名字牌，但模型内部的模块、钩子或子对象之间仍然互相指着彼此，导致它们的引用计数没有立刻归零。在引用计数归零前，PyTorch 缓存分配器依然把上一任模型的显存块标记为“存活占用”；就算你紧接着调用 `torch.cuda.empty_cache()`，分配器也无权回收这些“活块”，只能向驱动再申请一批新显存去装下一个模型。直到 Python 的循环垃圾回收器（`gc.collect()`）真正触发、剪断这层引用环，旧块才会退回空闲池并被 `empty_cache()` 归还。因此在单卡脚本里需要连续切换多个模型时，标准的清理顺序必须是三步连招：`del model` 断开外部引用 → `gc.collect()` 打破内部引用环 → `torch.cuda.empty_cache()` 把空闲池退还给设备驱动。这一机制也解释了为何 3.3.1 节必须采用加载前后差值法，以及为何设备级差值里会带有 $\pm 0.04\;\text{GiB}$ 的轻微波动。

### 4B 权重 +0.055 GiB 残差的逐字节归因

接着追查第二个悬念：3.3.1 节中，0.6B 和 1.7B 的 `torch allocated` 与理论公式误差都不到 0.001 GiB，为什么唯独 Qwen3-4B 多出了约 0.055 GiB？

为了排除多模型切换的干扰，在干净上下文中单独加载 Qwen3-4B，并导出 PyTorch 缓存分配器的底层内存快照（`results/residual_4b.json`），把每一笔字节摊开对账：

| 拆解项 | 精确字节数 | 换算（GiB） |
| --- | ---: | ---: |
| `torch.cuda.memory_allocated()` | $8{,}101{,}709{,}824\;\text{B}$ | $7.5453\;\text{GiB}$ |
| 398 个模型参数存储净字节之和 | $8{,}044{,}936{,}192\;\text{B}$ | $7.4924\;\text{GiB}$ |
| `named_buffers`（2 个 FP32 RoPE 频率缓冲） | $512\;\text{B}$ | $\approx 0$ |
| 净残差（`allocated − params − buffers`） | **$56{,}773{,}120\;\text{B}$** | **$0.0529\;\text{GiB}$** |
| 内存快照 400 个活跃块的 $\sum(\text{块尺寸} - \text{请求尺寸})$ | **$56{,}773{,}120\;\text{B}$** | **$0.0529\;\text{GiB}$** |

最后两行**逐字节完全相等**，连 1 个字节都不差。这彻底证明了那 56,773,120 字节既不是隐藏的神秘缓冲区，也不是驱动多算的开销，而是 PyTorch 缓存分配器的 **size-class 块对齐取整**（内碎片）。

把分配器想象成一家只提供固定标准尺寸纸箱的打包厂：为了方便切分和复用，工厂不按商品的精确毫米数定制纸箱，而是把大张量向上取整到最接近的标准箱型（例如 2 MiB 的整数倍）。Qwen3-4B 有 36 层，每层 MLP 包含 `gate`、`up`、`down` 三个大型权重矩阵，总计 108 个大矩阵。每个矩阵的净大小约为 47.53 MiB（略小于 48 MiB），装进标准纸箱时，分配器把它向上取整到 48 MiB，每个箱子里就白白多出约 0.5 MiB 的对齐空隙；把这 108 个大箱子的空隙加起来，光 MLP 就占去约 54 MiB，几乎包揽了全部 56,773,120 B 的残差，剩余不到 0.2 MiB 则来自其余较小物块的零星取整。相比之下，0.6B 和 1.7B 的单个权重张量尺寸更小、更贴近小档位对齐边界，余量停留在 KiB 级，所以在 GiB 视角下几乎隐身。这也提醒我们：看到 0.7% 左右的“多出来显存”时，不必急着怀疑代码写出了隐藏副本，先导出分配器快照核对块对齐余量，往往能立刻把账算平。

### 解析模拟器与 vLLM 实测 KV 池的对账

最后把 3.2 节的解析账本（假设 $M_{\mathrm{overhead}} = 0.5\;\text{GiB}$）与 3.3.3 节 vLLM 实测分到的 KV 池拉到同一张表上对账。以 Qwen3-4B（`util=0.9`）为例，解析账本给出的 KV 池上界是 **6.317 GiB**（46,000 token），而 vLLM 实际划出来的 KV 池是 **5.62 GiB**（40,928 token），实测约为解析上界的 **89%**。中间差出来的 **0.697 GiB** 到底去哪了？逐项拆解如下：

| 差额来源（模拟 − 实测） | 贡献（GiB） | 说明 |
| --- | ---: | --- |
| 总显存基准差 | $-0.020$ | 模拟取标称 $15.9 \times 0.9 = 14.31$，实卡为 $15.92 \times 0.9 = 14.33$ |
| 权重分配器取整差 | $+0.067$ | vLLM 实测权重 7.56 vs 公式 7.493 |
| vLLM 非权重常驻开销 | $+0.550$ | 进程运行时上下文与非 PyTorch 占用 |
| vLLM 激活峰值预留 | $+0.600$ | 启动 profiling 在分块预算下预留的激活空间 |
| 模拟器的固定预留项 | $-0.500$ | 3.2 节中已扣除的 $M_{\mathrm{overhead}}$ |
| **合计差额** | **$+0.697$** | 与 $6.317 - 5.620 = 0.697\;\text{GiB}$ 完全闭合 |

整张表严丝合缝地闭合到了小数点后第三位。结论随之水落石出：vLLM 在划拨 KV 池之前，实际扣除的非权重非 KV 开销包括两笔——0.55 GiB 的非权重常驻开销和 0.60 GiB 的启动激活峰值预留，合计 **1.15 GiB**。因此，3.2 节预设的 0.5 GiB 固定预留项，拿去估裸 PyTorch 稳态（底噪仅 0.196 GiB）时偏保守，但拿去估已经提前把激活峰值锁进预算的 vLLM 预分配池时又偏乐观。

在 Qwen3-1.7B（`util=0.9`）上做交叉验证同样印证了这一规律：解析上界为 99,287 token，vLLM 实测为 94,640 token，对账率高达 **95%**（因为 1.7B 的权重取整余量微乎其微，启动激活峰值也降到了 0.41 GiB）。据此可以提炼出一条实用的工程规划经验：如果只想用解析公式快速反推 vLLM 的真实 KV 池大小，可以把 0.5 GiB 预留版算出的结果乘以 0.85–0.95 的经验折减；如果要提高纸面模型的准确度，直接把 $M_{\mathrm{overhead}}$ 拆成“引擎非权重常驻 + 激活峰值预留（若启用 CUDAGraph 还要额外计入图捕获显存）”，大约设为 $1.0\text{–}1.2\;\text{GiB}$，就能在不开机启动引擎的前提下准确预判单卡容量。

## 实验：解析账本、三口径实测与残差对账

本实验复现本章的三组核心验证：手算与解析账本对账、三口径显存测量与 4B 逐字节残差归因，以及 vLLM 启动预分配与池饱和压测。如果手边没有 RX 9070 XT 或 ROCm 环境，可直接读取 `code/part1-modeling/chapter3/results/` 下的离线存档完成全部计算与核对。

### 步骤 1：运行解析显存账本（纯 CPU 即可）

进入仓库的 `code/part1-modeling/chapter3` 目录，运行解析账本模块：

```bash
cd code/part1-modeling/chapter3
python3 mem_ledger.py
python3 mem_ledger.py --model 4B --card 9070xt --util 0.9
```

打开输出文件 `results/mem_ledger.json`，核对 Qwen3-1.7B 与 4B 在 9070 XT 上的权重占用、每 token KV 字节数、KV 池总 token 数以及 $B_{\max}(4096)$，并与 3.2 节的手算结果对照。

### 步骤 2：三口径真机测量与 4B 残差归因

在配备 RX 9070 XT 的宿主机上运行裸 PyTorch 三口径脚本与 4B 残差分析脚本：

```bash
HIP_VISIBLE_DEVICES=1 python3 mem_real.py
HIP_VISIBLE_DEVICES=1 python3 residual_check.py
```

打开 `results/mem_real_9070xt.json` 与 `results/residual_4b.json`（无 GPU 时直接读取内置存档），完成三项检查：

1. 在 `mem_real_9070xt.json` 中读取 `a_baseline.context_overhead_gib`（0.196 GiB）与 `b_weights` 下三模型的 `formula_gib`、`torch_allocated_gib` 和 `rocm_smi_delta_gib`，核对误差是否在 1% 以内。
2. 读取 `c_kv_growth`、`d_prefill_peak.activation_spike_gib`（1.2539 GiB）和 `e_fragmentation.reserved_minus_allocated_gib`（0.1484 GiB），验证 KV 阶梯三口径是否重合。
3. 在 `residual_4b.json` 中比较 `gap_bytes` 与 `snapshot.block_padding_bytes`（均为 `56773120`），验证 4B 残差是否完全来自块对齐取整。

### 步骤 3：vLLM 启动账本与并发压测

在 `rocm/vllm` 容器内运行探测脚本（完整 `docker run` 参数见 `vllm_probe.py` 文件头部注释），或直接读取内置存档 `results/vllm_probe_9070xt.json`：

1. 在 `engines` 中对比 `qwen3_4b_u090_s4096`、`qwen3_4b_u090_s8192` 与 `qwen3_4b_u090_s16384` 的 `kv_tokens`（均为 40,928）与 `max_concurrency`（9.99 / 5.00 / 2.50），验证 `max_model_len` 不改变 KV 池大小。
2. 在 `stress` 中读取 `n_req` 为 2、4、8、16 时的 `wall_s`、`preemptions` 与 `tok_s_agg`，结合每条请求 4,352 token 的缓存需求，解释为何并发 16 时总耗时几乎翻倍而抢占次数仍为 0。

## 练习

1. 某模型共 $L = 32$ 层，隐藏维 $d = 4096$，采用 GQA（查询头 $H_q = 32$，键值头 $H_{\mathrm{kv}} = 8$，单头维度 $D_{\mathrm{head}} = 128$）。求 BF16 口径下每 token 的 KV 缓存字节数（单位 KiB）。如果改回 MHA（$H_{\mathrm{kv}} = 32$），每 token 占用会变为多少？
2. 一张 24 GiB 显存的 GPU 运行上述 BF16 模型（权重占 14.0 GiB），设定显存使用率上限 $u = 0.9$，预计非权重非 KV 运行时开销（含上下文与激活预留）为 1.2 GiB。计算可供 KV 缓存使用的显存 $M_{\mathrm{avail}}$、池容量（token 数），以及在单条请求平均长度 $S = 4096$ 时的最大并发数 $B_{\max}(4096)$。
3. 沿用第 2 题条件。如果将该模型权重从 BF16 量化到 INT4（权重降至约 3.8 GiB，KV 缓存仍保持 BF16 不变），可用 KV 池容量与 $B_{\max}(4096)$ 会分别变成多少？
4. 在 3.3.3 节的 vLLM 启动表中，Qwen3-4B 在 `util=0.9` 下无论 `max_model_len` 设为 4096 还是 16384，KV 池都固定为 40,928 token。某同学希望把 4B 在 8192 长度下的最大并发数提高一倍，于是将 `max_model_len` 从 16384 调小到 8192，期望以此腾出更多显存给 KV 池。这个操作能增大 KV 池吗？真正能增大 KV 池的手段有哪些？
5. 在裸 PyTorch 顺序加载两个模型后，设备驱动工具 `rocm-smi` 报告已用显存 8.50 GiB，而 `torch.cuda.memory_allocated()` 仅报告 5.20 GiB，同时 `torch.cuda.memory_reserved()` 报告 8.30 GiB，已知运行时上下文底噪为 0.20 GiB。说明这三个读数之间的关系，并解释为什么 `reserved` 会比 `allocated` 多出 3.10 GiB。
6. 3.3.2 节测得 Qwen3-1.7B 单发 4096-token 预填充的激活峰值为 1.2539 GiB，而 3.3.3 节 vLLM 对同一模型报告的激活峰值为 0.41 GiB。为什么同一模型的激活峰值读数相差超过三倍？能否用“1.2539 − 0.41”来计算 vLLM 省下了多少稳态显存？
7. 在 3.4 节的对账表中，为什么 0.5 GiB 的固定预留项在 Qwen3-4B（`util=0.9`）上高估了 vLLM 的 KV 池（模拟 46,000 token vs 实测 40,928 token）？如果要让解析模拟器在预测 vLLM 池容量时误差更小，应把 $M_{\mathrm{overhead}}$ 调整为包含哪两项开销？

::: details 参考答案

1. GQA 下 $m_{\mathrm{kv}} = 2 \times 32 \times 8 \times 128 \times 2 = 131{,}072\;\text{B} = 128\;\text{KiB/token}$。若改回 MHA（$H_{\mathrm{kv}} = 32$），键值头变为 4 倍，每 token 占用增至 $512\;\text{KiB/token}$。
2. 总预算 $24 \times 0.9 = 21.6\;\text{GiB}$；可用池 $M_{\mathrm{avail}} = 21.6 - 14.0 - 1.2 = 6.4\;\text{GiB}$。换算成 token 数：$6.4 \times 1024^2 / 128 = 52{,}428.8 \to 52{,}428\;\text{tokens}$。在 $S = 4096$ 下，最大并发 $B_{\max}(4096) = \lfloor 52{,}428 / 4096 \rfloor = 12$。
3. 权重降至 3.8 GiB 后，$M_{\mathrm{avail}} = 21.6 - 3.8 - 1.2 = 16.6\;\text{GiB}$；池容量增至 $\lfloor 16.6 \times 1024^2 / 128 \rfloor = 135{,}987\;\text{tokens}$；$B_{\max}(4096) = \lfloor 135{,}987 / 4096 \rfloor = 33$（并发上限提升近 2.75 倍）。
4. 不能增大 KV 池。vLLM 在启动时把预算内的剩余显存全部分配给 KV 池，`max_model_len` 只限制单条请求的最大允许长度，不改变池总容量。真正能增大 KV 池的方法包括：提高 `gpu_memory_utilization`、对权重或 KV 进行量化、减少 CUDAGraph/激活预留，或更换更大显存的显卡（以及多卡并行分摊权重）。
5. 设备级读数等于上下文底噪加上分配器保留池：$0.20 + 8.30 = 8.50\;\text{GiB}$。`reserved` 比 `allocated` 多出的 3.10 GiB 既包含分配器的块对齐与空闲缓存块，也常包含前一个已删除但尚未被 Python 垃圾回收彻底释放的模型张量块。
6. 两者测量的工作负载与执行机制不同：前者是裸 PyTorch 对单条 4096-token 序列一次性完成完整预填充时的瞬态峰值，后者是 vLLM 在分块预填充引擎与融合算子路径下按启动 profiling 预算测出的峰值。此外，激活工作区是瞬态峰值而非稳态常驻占用，因此不能直接相减并解释为“稳态节省”。
7. 因为 vLLM 预分配池时同时扣除了非权重常驻开销（0.55 GiB）和启动 profiling 测得的激活峰值预留（0.60 GiB），合计 1.15 GiB，加上 4B 权重块取整（0.067 GiB），远大于模拟器假设的 0.5 GiB。要提高对 vLLM 池容量的预测精度，应将 $M_{\mathrm{overhead}}$ 明确拆为“引擎运行时非权重常驻开销 + 激活峰值预留（若启用 CUDAGraph 还需加上图捕获预留）”。

:::
